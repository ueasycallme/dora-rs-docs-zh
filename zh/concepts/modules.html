Dora 用户指南

模块（可复用子数据流）

模块让你可以在单独的 YAML 文件中定义可复用的节点子图，并将其组合成更大的数据流。模块会在编译期展开——运行时从不会看到它们。

快速开始

Module file（modules/transform_module.yml）：

module:
  name: transform_pipeline
  inputs: [raw_data]
  outputs: [filtered]

nodes:
  - id: doubler
    path: doubler.py
    inputs:
      data: _mod/raw_data
    outputs:
      - doubled

  - id: filter
    path: filter_even.py
    inputs:
      data: doubler/doubled
    outputs:
      - filtered

Dataflow file（dataflow.yml）：

nodes:
  - id: sender
    path: sender.py
    outputs:
      - value

  - id: pipeline
    module: modules/transform_module.yml
    inputs:
      raw_data: sender/value

  - id: receiver
    path: receiver.py
    inputs:
      filtered: pipeline/filtered

展开后，pipeline 变成两个节点：pipeline.doubler 和 pipeline.filter，所有连线都会自动解析。

模块定义文件

一个模块文件包含两个部分：

module: 头部

字段类型必填描述
namestring是模块名称（仅用作元数据）
inputslist否必需的输入端口名称
inputs_optionallist否可选的输入端口（未接线时会静默跳过）
outputslist否暴露给父数据流的输出端口名称

只要 Dora 加载该模块，模块头部中的未知字段都会被拒绝，这包括 dora expand、dora build 和 dora run。

nodes: 列表

标准的节点定义，但带有一种特殊语法：_mod/port_name 用于引用模块的输入端口。展开时，_mod/port_name 会被父级接到该端口上的内容替换。

module:
  name: my_module
  inputs: [camera_feed]
  outputs: [detections]

nodes:
  - id: detector
    path: detect.py
    inputs:
      image: _mod/camera_feed    # resolved to parent's wiring
    outputs:
      - detections

模块级构建

模块可以有一个顶层的 build: 命令，它会在任何内部节点构建之前运行：

module:
  name: ml_pipeline
  inputs: [image]
  outputs: [result]

build: pip install -r requirements.txt

nodes:
  - id: model
    path: model.py
    inputs:
      image: _mod/image
    outputs:
      - result

使用模块

在数据流节点中使用 module: 字段（而不是 path:）来引用模块：

- id: nav_stack
  module: modules/navigation.module.yml
  inputs:
    goal_pose: localization/goal

模块节点的 inputs: 映射会把父级的输出接到模块的输入端口上。外部节点通过 <module_id>/<output_name>（例如 nav_stack/cmd_vel）来引用模块的输出。

参数

通过 params: 将配置值传递给模块：

- id: fast_pipeline
  module: modules/transform_module.yml
  inputs:
    raw_data: sender/value
  params:
    speed: "2.0"
    mode: turbo

在模块内部，使用 $PARAM_<UPPERCASE_KEY> 在 args: 中引用参数：

nodes:
  - id: processor
    path: processor.py
    args: --speed $PARAM_SPEED --mode $PARAM_MODE
    inputs:
      data: _mod/raw_data
    outputs:
      - result

参数同时会作为环境变量（PARAM_SPEED、PARAM_MODE）注入到模块内的每个节点中。

展开规则

  1. 加载模块的 YAML 文件并验证其头部
  2. 为所有内部节点 ID 加上 {module_id}. 前缀（例如 nav_stack.planner）
  3. 用父级输入映射中的实际来源替换 _mod/port_name 引用
  4. 重写内部的交叉引用（例如 planner/path 会变成 nav_stack.planner/path）
  5. 将模块声明的输出映射到内部节点的输出，因此 nav_stack/cmd_vel 会解析为 nav_stack.controller/cmd_vel。内部节点可以通过其节点级的 outputs:、operator:/operators: 块，或旧式的 custom: 块来产生所声明的输出。对于由 operators: 节点的算子产生的输出，解析后的引用会保留运行时节点所需的 operator 分段：nav_stack/cmd_vel 会解析为 nav_stack.runtime/controller/cmd_vel
  6. 用展开后的扁平节点替换模块节点
  7. 在 args: 字段中替换 params: 的值，并作为环境变量注入

使用 dora expand 查看结果：

dora expand dataflow.yml

嵌套模块

模块可以引用其他模块。展开过程是递归的，深度上限为 8 层：

# outer_module.yml
module:
  name: outer
  inputs: [data]
  outputs: [result]

nodes:
  - id: inner
    module: inner_module.yml
    inputs:
      raw: _mod/data

  - id: postprocess
    path: postprocess.py
    inputs:
      data: inner/processed
    outputs:
      - result

展开后，节点 ID 是完全限定的：outer.inner.some_node。

只有嵌套模块声明的输出对其父级可见。在上面的例子中，父模块可以接线或重新导出 inner/processed，因为 processed 列在 inner_module.yml 的 module.outputs 中；但它无法访问 inner_module.yml 内部节点产生的私有输出。

可选输入

当一个模块应该在有无某些连接的情况下都能工作时，将输入声明为可选：

module:
  name: flexible_processor
  inputs: [data]
  inputs_optional: [config]
  outputs: [result]

nodes:
  - id: processor
    path: processor.py
    inputs:
      data: _mod/data
      config: _mod/config    # silently dropped if not wired
    outputs:
      - result

当父级没有接线 config 时，该输入只是会从展开后的节点中省略。

可视化

dora graph 会将模块边界渲染为 Mermaid 子图，便于查看每个节点来自哪个模块：

dora graph dataflow.yml --open

验证

在没有完整数据流的情况下单独验证一个模块文件：

dora expand --module modules/transform_module.yml

这会检查：

  • YAML 结构是否有效
  • 模块头部是否存在，且包含必需的 name、可选的 inputs/outputs，并且没有未知的头部字段
  • 所有 _mod/ 引用都对应已声明的输入或可选输入
  • 每个声明的输出都由某个内部节点产生（包括 operator:/operators: 以及旧式的 custom: 输出）
  • 没有重复的节点 ID
  • 内部接线是一致的
  • 嵌套模块文件存在、是相对路径、无环，并且在嵌套深度上限之内

以上每一项检查都会递归运行：嵌套模块文件会被完整验证，而不仅仅是读取其声明的输出。

一个声明的输出必须恰好有一个生产者。如果两个内部节点发出了同名的输出，且该名称同时列在 module.outputs 中，展开会失败，而不是悄悄选取第一个生产者。module.outputs 只是一个普通列表，没有 output: node/port 这种映射语法，因此修复方式是重命名未被导出的内部信号。这一规则适用于 dora run 和 dora build，不仅仅是 dora expand。

模块内部的源路径解析

模块内部节点的 path:，以及其算子的 shared-library:、python: 和 wasm: 值，都是相对于模块文件所在目录解析的，而不是相对于顶层数据流。位于 modules/nested/ 中的模块声明 python: op.py，指的是 modules/nested/op.py。

重写规则不适用于以下情形：URL、绝对路径，以及 dynamic 和 shell 哨兵值（守护进程会对其进行逐字匹配）。

值得了解的两个后果：

  • 解析后逃出数据流目录的路径会被拒绝。模块无法通过 python: ../shared/op.py 访问同级项目，示例数据流中使用的 ../../target/debug/<bin> 写法也无法在模块内部使用。
  • build: 命令仍以 数据流 目录作为工作目录运行。因此构建产生的构件必须从构建实际放置它的位置引用，而这并不是模块目录——所以模块内 build: cargo build -p my-op 搭配 shared-library: target/debug/my-op 会被解析为 modules/target/debug/my-op，从而找不到该文件。请使用绝对路径，或将此类节点保留在顶层数据流中。

安全

  • 路径限制：模块文件路径必须在词法上被包含于项目根目录内，并在物理上被包含于根目录或树内符号链接的目标之内。超出这些边界的绝对路径和目录穿越（../）都会被拒绝。
  • 文件大小限制：模块文件上限为 1 MB。
  • 深度限制：递归嵌套上限为 8 层。
  • 参数键校验：参数键只能由字母数字和下划线组成。
