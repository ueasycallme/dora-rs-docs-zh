Dora 用户指南

Dora 架构

Dora（AI-Dora，Agentic Dataflow-Oriented Robotic Architecture）的完整架构参考——一个完全使用 Rust 编写的实时机器人与 AI 应用框架。

概览与设计理念

Dora 建立在四项核心原则之上：

  1. 面向数据流（Dataflow-oriented）：应用程序是由带类型的数据通道连接的节点组成的有向图。节点声明输入和输出；框架负责路由、调度和生命周期管理。
  2. 零拷贝性能：超过 4 KiB 的消息使用带有 128 字节对齐缓冲区和原子协调的共享内存，延迟比 ROS2 低 10-17 倍。
  3. 多语言支持：对 Rust、Python（PyO3）、C 和 C++ 节点提供一流支持——全部共享同一种 Apache Arrow 数据格式。
  4. 四层架构：消息协议、核心库、守护进程/运行时执行，以及 CLI/协调器编排。

组件架构

CLI

dora 命令提供三组命令：

生命周期（run、up、down、build、start、stop、restart）：

  • dora run 在本地执行数据流，无需协调器/守护进程（单机快捷方式）
  • dora up / dora down 管理协调器 + 守护进程基础设施
  • dora start / dora stop 控制运行中协调器上的数据流

监控（list、logs、inspect、topic、node、record、replay、trace）：

  • 使用 dora inspect top 进行实时检查
  • 话题订阅与数据检查
  • 通过 .drec 文件进行录制和回放

设置（status、new、graph、system、completion、self）：

  • 项目脚手架、数据流可视化、自我更新

协调器

协调器是一个基于 Axum 的 WebSocket 服务器，负责编排分布式部署。

                          ┌──────────────────┐
                          │   Coordinator     │
            WS /api/control  │  ┌────────────┐  │  WS /api/daemon
   CLI ◄──────────────────►  │  │   State    │  │ ◄──────────────────► Daemon(s)
                          │  │   Store    │  │
                          │  └────────────┘  │
                          │  /api/artifacts  │
                          │  /health         │
                          └──────────────────┘

WebSocket 路由：

  • /api/control——CLI 控制平面（build、start、stop、list、logs、topic subscribe）
  • /api/daemon——守护进程注册与事件流
  • /api/artifacts/{build_id}/{node_id}——二进制构件下载
  • /health——健康检查端点

状态管理：默认为内存存储，可通过 redb 后端实现持久化存储。

守护进程

每台机器运行一个守护进程，管理该机器上所有节点的生命周期。

事件循环（Daemon::run_inner()）：合并以下内容的异步 Tokio 事件循环：

  • 协调器命令（WebSocket）
  • 节点事件（TCP/共享内存）
  • 守护进程间事件（Zenoh）
  • 心跳（5 秒间隔）、指标采集（2 秒）、健康检查（默认 5 秒）

节点启动：

  1. 为节点创建工作目录
  2. 设置通信通道（TCP 或 shmem）
  3. 将 NodeConfig 序列化为环境变量
  4. 以经过净化的环境启动进程（阻止 LD_PRELOAD、DYLD_INSERT_LIBRARIES 等）
  5. 通过 ProcessHandle 监控

运行时

运行时在一个专用进程中执行进程内算子（Python、共享库、WASM）。

│          Runtime             │
│                              │
│  ┌────────────────────────┐  │
│  │ Operator Runner        │  │
│  │ (separate thread)      │  │
│  │                        │  │
│  │ SharedLibrary → dlopen │  │
│  │ Python → PyO3          │  │
│  │ Wasm → (planned)       │  │

│             │ flume(2)       │
│  ┌──────────▼─────────────┐  │

│  │ └─ DaemonEvent         │  │
│  └────────────────────────┘  │

  • 单线程 Tokio 运行时
  • 算子运行在独立线程中，通过 flume::bounded(2) 通道通信
  • 每个数据 ID 的输入队列大小可配置（默认：10）

节点

节点是与守护进程通信的独立进程。

生命周期：

  1. 节点启动，从环境变量读取 NodeConfig
  2. 通过 DaemonRequest::Register 向守护进程注册
  3. 通过 DaemonRequest::Subscribe 订阅事件
  4. 在循环中处理事件（NextEvent → 处理 → SendMessage）
  5. 报告丢弃令牌以清理共享内存
  6. 通过 OutputsDone 发出完成信号

守护进程到节点（本地）

三种传输方式，通过 LocalCommunicationConfig 配置：

TCP（默认）：

  • 绑定 127.0.0.1:0（临时端口），启用 TCP_NODELAY
  • 帧格式：[8-byte u64 LE length][postcard payload]
  • 最大消息：64 MiB，读取超时：30 秒

共享内存（零拷贝）：

  • 每个节点四个 4 KiB 区域：control、events、drop tokens、events-close
  • 用于大小 ≥ 4096 字节的消息（ZERO_COPY_THRESHOLD）
  • 采用 acquire/release 顺序的原子同步

节点 → 守护进程请求： Register、Subscribe、SendMessage、CloseOutputs、OutputsDone、NextEvent、ReportDropTokens、SubscribeDrop、NodeConfig。

守护进程 → 节点回复： Result、PreparedMessage、NextEvents、NextDropEvents、NodeConfig、Empty。

节点事件： Stop、Reload、Input、InputClosed、InputRecovered、NodeRestarted、AllInputsClosed。

同步协议

发送（写入 → 以 release 方式存储长度 → 发出事件信号 → 检查断开连接）：

  1. 将数据复制到共享内存缓冲区
  2. 以 Release 顺序存储消息长度（发布数据）
  3. 发出事件信号以唤醒接收方
  4. 使用 Acquire 顺序检查断开连接标志

接收（等待事件 → 检查断开连接 → 以 acquire 方式加载长度 → 读取数据）：

  1. 等待事件信号
  2. 使用 Acquire 顺序检查断开连接标志
  3. 以 Acquire 顺序加载消息长度（确保所有写入可见）
  4. 从缓冲区读取并反序列化数据

DropToken 生命周期

  1. 发送方分配共享内存，生成 DropToken（UUIDv7）
  2. 发送方传输 DataMessage::SharedMemory { shared_memory_id, len, drop_token }
  3. 接收方处理数据，通过 ReportDropTokens 返回 drop_token
  4. 发送方收到确认的 token 后，将内存返还给缓存以供复用

重启策略

每个节点的配置字段：

  • max_restarts——0 表示无限制
  • restart_delay——初始重试延迟（秒），每次尝试翻倍
  • max_restart_delay——限制指数退避的上限
  • restart_window——N 秒后重置计数器（实现“每 M 秒 N 次重启”）
  • health_check_timeout——若在此时长内无活动则终止节点

健康监控

  • 心跳间隔：5 秒（守护进程 → 协调器）
  • 健康检查间隔：5 秒（可按数据流配置）
  • 指标采集：间隔 2 秒（CPU、内存、磁盘、待处理消息）

熔断器（Circuit Breaker）

基于单个输入的超时检测，并支持自动恢复：

  1. 输入配置了 input_timeout: <seconds>
  2. 若在超时时间内未收到数据 → 向节点发送 InputClosed 事件
  3. 节点将该输入标记为降级（degraded），可使用缓存的最后已知值
  4. 当上游恢复 → 触发 InputRecovered 事件，熔断器重新开启
  5. 节点状态转换：Running → Degraded → Running

Zenoh 话题命名

dora/{network_id}/{dataflow_id}/output/{node_id}/{output_id}
  • network_id 用于隔离不同的 Dora 集群（默认值："default"）
  • Zenoh 路由器端口：7447，peer 端口：5456
  • 路由模式：linkstate

构建分发

通过 DistributeStrategy 提供三种策略：

  • Local——每个守护进程从源代码构建（默认）
  • Scp——CLI 通过 SSH/SCP 推送已构建的二进制文件
  • Http——守护进程从协调器的 /api/artifacts 端点拉取

机器标签

deploy:
  labels:
    gpu: "true"
    arch: "arm64"

录制与回放

.drec 二进制格式

[HEADER]
├─ MAGIC: 8 bytes ("DORAREC")
├─ version: u16 LE (currently 1)
├─ start_nanos: u64 LE (Unix epoch nanoseconds)
├─ dataflow_id: 16 bytes (UUID)
├─ yaml_len: u32 LE
└─ descriptor_yaml: [u8; yaml_len]

[ENTRIES] (repeated)
├─ record_len: u32 LE
├─ node_id_len: u16 LE
├─ node_id: [u8; node_id_len]
├─ output_id_len: u16 LE
├─ output_id: [u8; output_id_len]
├─ timestamp_offset_nanos: u64 LE
├─ event_bytes_len: u32 LE
└─ event_bytes: [u8; event_bytes_len]    (postcard InterDaemonEvent)

[FOOTER] (optional, written on clean finish)
├─ FOOTER_MAGIC: 8 bytes ("DORAEND")
├─ total_messages: u64 LE
└─ total_bytes: u64 LE

扩展

遥测

分布式追踪（dora-tracing）：

  • OpenTelemetry 配合 OTLP 导出器（兼容 Jaeger、Zipkin、Tempo）
  • 跨节点的上下文传播
  • 设置：set_up_tracing(name: &str)

指标（dora-metrics）：

  • 通过 sysinfo 获取系统指标（CPU、内存、磁盘）
  • 配合 OTLP 导出器的 OpenTelemetry meter
  • 异步进程观测器：run_metrics_monitor(meter_id)

ROS2 桥接

基于 YAML 的声明式 ROS2 集成，支持：

Topics——订阅（ROS2 → Dora）或发布（Dora → ROS2）：

ros2:
  topic: /camera/image
  message_type: sensor_msgs/Image
  direction: subscribe

Services（服务）——客户端或服务端角色：

ros2:
  service: /add_two_ints
  service_type: example_interfaces/AddTwoInts
  role: client

Actions（动作）——目标 / 反馈 / 结果生命周期：

ros2:
  action: /fibonacci
  action_type: example_interfaces/Fibonacci
  role: client

QoS 配置：

qos:
  reliable: true
  durability: transient_local
  keep_last: 10
