Dora 用户指南

日志记录

dora 为实时机器人与 AI 数据流提供了一套结构化日志系统。日志按节点捕获为结构化 JSONL 文件，转发给协调器以进行实时流传输，并可选地作为数据消息通过数据流图路由。

应该使用哪种日志记录方式？

如果你不确定哪种方式适合你的用例，可以从这里开始。

我想……方式配置
从 Python 记录日志使用 Python 的 logging 模块（自动桥接）无需任何操作——只需 import logging
从 Rust 记录日志使用 node.log_info() / node.log_error() 等无——开箱即用
从 C/C++ 记录日志使用 dora_log() / log_message()无——开箱即用
过滤噪声节点在 YAML 中设置 min_log_level逐节点 YAML 字段
在一处查看所有日志订阅 dora/logs 虚拟输入inputs: logs: dora/logs
将某个节点的日志作为数据处理在该节点上使用 send_logs_as逐节点配置 YAML 并接入输出
轮转日志文件在 YAML 中设置 max_log_size逐节点 YAML 字段
构建自定义日志接收器使用 dora-log-utils crateRust 依赖项
过滤 CLI 显示使用 --log-level / --log-filter 标志CLI 标志或环境变量

各语言的快速开始

Python——最简单的方式是使用 Python 内置的 logging 模块：

import logging
from dora import Node

node = Node()  # Automatically bridges Python logging -> dora

logging.info("Sensor started")       # Captured as structured "info" log
logging.warning("High temp: 42C")    # Captured as structured "warn" log
print("raw debug output")            # Captured as "stdout" level

当创建 Node() 时，它会安装一个处理器，将所有 Python logging 调用都路由到 Rust 的 tracing 系统中。守护进程会将这些调用解析为带有级别、消息、文件和行号的结构化日志条目。无需额外配置。

你也可以使用显式 API 来设置结构化字段：

node.log_info("Reading acquired")
node.log("info", "Reading acquired", fields={"sensor_id": "temp-01"})

Rust——使用节点 API 提供的便捷方法：

#![allow(unused)]
fn main() {
let (node, mut events) = DoraNode::init_from_env()?;

// Convenience methods (recommended for most cases)
node.log_info("Sensor started");
node.log_warn("High temperature");

// With structured fields
let mut fields = BTreeMap::new();
fields.insert("sensor_id".into(), "temp-01".into());
node.log_with_fields("info", "Reading acquired", None, Some(&fields));
}

此外，Rust 节点也可以使用 tracing crate。当初始化了 dora 的 tracing 订阅者（通过 init_tracing()）之后，tracing::info!() 等调用会将结构化 JSON 输出到 stdout，守护进程会自动解析：

#![allow(unused)]
fn main() {
// Also works -- parsed as structured logs by the daemon
tracing::info!("Sensor started");
tracing::warn!(sensor_id = "temp-01", "High temperature");
}

当你希望对日志格式进行显式控制时，使用 node.log_*()。当你希望与生态系统集成（span、instrumentation、OpenTelemetry）时，使用 tracing::*!()。两者在守护进程中产生的结构化日志条目是相同的。

C——使用 dora_log() 函数：

dora_log(ctx, "info", 4, "Sensor started", 14);

C++——使用 log_message() 函数：

log_message(node.send_output, "info", "Sensor started");

日志文件格式

每个节点都会在以下位置生成一个 JSONL 文件（每行一个 JSON 对象）：

<working_dir>/out/<dataflow_uuid>/log_<node_id>.jsonl

每一行的结构如下：

{
  "timestamp": "2024-01-15T10:30:00.123Z",
  "level": "info",
  "node_id": "sensor",
  "message": "Starting sensor...",
  "target": "sensor::module",
  "fields": { "key": "value" }
}
字段类型描述
timestampstring精确到毫秒的 RFC3339 时间戳
levelstring"error"、"warn"、"info"、"debug"、"trace" 或 "stdout"
node_idstring节点 ID
messagestring日志消息文本
targetstring?Rust 模块目标（例如 "sensor::module"），缺失时为 null
fieldsobject?来自日志框架的结构化键值字段。信任模型： 字段来自节点的 stdout，未经消毒即直接传递。在混合信任环境中，日志消费者在据此采取行动前应先校验字段内容

节点输出如何变为日志条目

守护进程会捕获节点进程 stdout/stderr 的每一行，并尝试将其解析为结构化日志消息（带有 level、message、timestamp 以及可选 fields 的 JSON）。如果解析成功，结构化字段会被保留；如果解析失败，原始行会成为一条 "stdout" 级别的条目。

这意味着使用 Rust 的 tracing 或 log crate 并以 JSON 格式输出的节点会自动获得完整的结构化日志。而只是简单 println! 的节点会产生 "stdout" 级别的条目。

查看日志：dora run

使用 dora run 运行数据流时，所有节点的日志都会在终端中实时显示。

标志

dora run dataflow.yml [OPTIONS]
标志默认值环境变量描述
--log-level LEVELstdoutDORA_LOG_LEVEL显示的最低级别
--log-format FORMATprettyDORA_LOG_FORMAT输出格式：pretty、json、compact
--log-filter FILTER无DORA_LOG_FILTER按节点覆盖级别

日志级别

从最详细到最简略依次为：

级别描述
stdout包含节点的原始 stdout 的所有内容（默认）
trace细粒度的诊断消息
debug开发者级别的诊断消息
info一般性信息消息
warn警告情况
error仅错误情况

设置 --log-level info 会隐藏 stdout、trace 和 debug 消息。stdout 级别是一个特殊的全收集级别，会放行所有内容。

级别过滤逻辑

级别过滤器使用 LogLevelOrStdout::passes()：

Message level    Filter level    Displayed?
─────────────    ────────────    ──────────
stdout           stdout          yes
stdout           info            no       (stdout only passes stdout filter)
info             stdout          yes      (any log level passes stdout filter)
debug            info            no       (debug is more verbose than info)
error            info            yes      (error is less verbose than info)

按节点覆盖

--log-filter 标志可以为不同节点设置不同的级别：

dora run dataflow.yml --log-level info --log-filter "sensor=debug,planner=warn"

这会对所有节点显示 info 及以上级别，除了 sensor（显示 debug 及以上）和 planner（显示 warn 及以上）。

格式："node1=level,node2=level"（以逗号分隔的 name=level 对）。

输出格式

Pretty（默认）——彩色、人类可读：

10:30:00 INFO   sensor: Starting sensor...

10:30:01 INFO   [dora]: spawning node processor

10:30:01 stdout sensor: raw output line
  • 本地时区的时间戳（HH:MM:SS）
  • 带颜色的级别：ERROR（红色）、WARN（黄色）、INFO（绿色）、DEBUG（蓝色）、TRACE（暗淡）、stdout（斜体暗淡蓝色）
  • 节点名以粗体显示，颜色根据名称唯一生成
  • 系统消息前缀为 [dora]
  • 生命周期消息（spawning、node finished、stopping）会通过空行进行视觉分隔

Json——完整的 LogMessage 结构体以 JSON 形式输出，每行一条：

{"build_id":null,"dataflow_id":"abc-123","node_id":"sensor","level":"INFO","message":"Starting...","timestamp":"2024-01-15T10:30:00Z",...}

适用于传给 jq 处理或导入日志聚合系统。

Compact——极简，无颜色：

10:30:00 INFO sensor: Starting sensor...

适用于 CI/CD 环境和日志文件。

查看日志：dora logs

读取历史日志或从正在运行的数据流中流式查看实时日志。

基本用法

# Read logs for a specific node (via coordinator)
dora logs <dataflow_uuid> <node_name>

# Read local log files directly
dora logs --local <node_name>
dora logs --local --all-nodes

# Stream live logs
dora logs <dataflow_uuid> <node_name> --follow
dora logs --local <node_name> --follow

标志

标志简写默认值描述
--localfalse从本地 out/ 目录读取，而不是从协调器读取
--all-nodesfalse合并所有节点的日志，按时间戳排序
--tail N-nall仅显示最后 N 行
--follow-ffalse在新日志条目到达时进行流式显示
--since DURATION无仅显示比该时长更新的日志
--until DURATION无仅显示比该时长更旧的日志
--level LEVELstdout最低日志级别（环境变量：DORA_LOG_LEVEL）
--grep PATTERN无不区分大小写的文本搜索
--coordinator-addr IP127.0.0.1协调器地址
--coordinator-port PORT默认值协调器控制端口

时间过滤器

--since 和 --until 接受相对于当前时间的时长字符串：

# Logs from the last 5 minutes
dora logs --local sensor --since 5m

# Logs from 1 hour ago to 30 minutes ago
dora logs --local sensor --since 1h --until 30m

# Last 10 errors from the past hour
dora logs --local sensor --since 1h --level error --tail 10

支持的时长格式：30（秒）、30s、5m、1h、2d。

文本搜索

--grep 对以下内容执行不区分大小写的子串匹配：

  • 日志消息文本
  • 节点 ID
  • 模块目标
# Find all timeout-related messages
dora logs --local --all-nodes --grep "timeout"

# Find errors from a specific module
dora logs --local sensor --grep "camera::driver" --level error

过滤流水线

所有过滤器按以下顺序应用：

Read/Parse -> Time Filters -> Grep -> Tail -> Display

在协调器模式下使用 --since、--until 或 --grep 时，CLI 会从服务器获取所有日志（忽略服务器端的 --tail），并在客户端应用所有过滤器。这确保了组合使用多个过滤器时能得到正确的结果。

本地模式与协调器模式

本地模式（--local）直接从当前工作目录下的 out/ 目录读取 JSONL 文件，无需运行协调器或守护进程。如果使用了 --all-nodes 或未指定节点名，则所有日志文件都会被合并并按时间戳排序。

协调器模式（默认）通过 WebSocket 连接到正在运行的协调器。协调器从守护进程的工作目录读取日志文件并流式回传。该模式同时适用于本地部署和分布式部署。

跟随模式

本地跟随（Local follow）（--local --follow）：每 200 毫秒轮询日志文件以获取新内容。新行会被解析、按 --grep 过滤并打印。时间/尾部过滤器仅应用于初始的历史输出。

协调器跟随（Coordinator follow）（--follow）：向协调器打开一个 WebSocket 订阅。协调器会实时转发来自守护进程的日志消息。为提高效率，级别过滤在服务器端进行。--grep 和 --since 则在客户端对数据流进行过滤。

环境变量

所有环境变量都仅作为后备——CLI 标志始终优先。

变量使用方取值描述
DORA_LOG_LEVELdora run, dora logserror, warn, info, debug, trace, stdout默认的最低日志级别
DORA_LOG_FORMATdora runpretty, json, compact默认输出格式
DORA_LOG_FILTERdora run"node1=level,node2=level"默认值 / 按节点覆盖
DORA_QUIET守护进程任意值禁止将日志转发到显示端（文件写入仍继续）

示例：

# Set defaults for a development session
export DORA_LOG_LEVEL=info
export DORA_LOG_FORMAT=pretty
export DORA_LOG_FILTER="sensor=debug"

# These are equivalent:
dora run dataflow.yml
dora run dataflow.yml --log-level info --log-format pretty --log-filter "sensor=debug"

# CLI flag overrides env var:
dora run dataflow.yml --log-level debug   # overrides DORA_LOG_LEVEL=info

YAML 配置

min_log_level

在日志到达日志文件、协调器或 send_logs_as 路由之前，在源头（守护进程端）对其进行过滤。

nodes:
  - id: noisy-sensor
    path: ./target/debug/sensor
    min_log_level: info    # suppress debug/trace/stdout from this node

有效取值：error、warn、info、debug、trace、stdout。

设置后，守护进程会在解析完成后立即丢弃低于该级别的日志消息。这可以减少磁盘 I/O、网络流量和日志文件大小。该过滤使用与 CLI 显示过滤器相同的 passes() 逻辑。

send_stdout_as

将原始的 stdout/stderr 行作为数据流输出消息进行路由。

nodes:
  - id: legacy-node
    path: ./legacy-script.py
    send_stdout_as: raw_output
    outputs:
      - raw_output
      - data

  - id: log-consumer
    inputs:
      logs: legacy-node/raw_output

每一行 stdout/stderr 都会以 Arrow 编码字符串的形式发送。这对于集成那些将数据输出到 stdout 的旧节点（例如使用 print() 的 Python 脚本）很有用。

send_stdout_as 与正常的日志文件写入会同时发生——stdout 路由不会抑制日志文件的写入。

send_logs_as

将已解析的结构化日志条目作为数据流输出消息进行路由。

nodes:
  - id: sensor
    path: ./target/debug/sensor
    send_logs_as: log_entries
    outputs:
      - data
      - log_entries

  - id: log-aggregator
    inputs:
      sensor_logs: sensor/log_entries

与 send_stdout_as 不同，这里只发送成功解析为结构化日志的行（而非原始 stdout）。每个条目都会序列化为完整的 JSON LogMessage 字符串。min_log_level 过滤器会在路由之前生效——被抑制的消息不会被发送。

可以利用这一点在数据流内部构建日志聚合、告警或监控节点。

dora/logs——自动日志聚合

只需一行输入即可订阅所有节点的日志——无需手动连线：

nodes:
  - id: sensor
    path: sensor.py
    inputs:
      tick: dora/timer/millis/200
    outputs:
      - reading

  - id: processor
    path: processor.py
    inputs:
      reading: sensor/reading
    outputs:
      - result

  - id: log-viewer
    path: log_viewer.py
    inputs:
      logs: dora/logs              # all nodes, all levels
      errors: dora/logs/error      # only error+ from all nodes
      sensor: dora/logs/info/sensor  # info+ from one node

dora/logs 虚拟输入的工作方式与 dora/timer 类似——订阅由守护进程在内部处理。每条日志消息都会以 Arrow 数组中经 JSON 编码的 LogMessage 字符串形式到达。为防止无限循环，节点永远不会收到自己的日志消息。

语法：

输入描述
dora/logs所有节点的所有日志
dora/logs/<level>所有节点中级别为 <level> 及以上的日志
dora/logs/<level>/<node-id>指定节点中级别为 <level> 及以上的日志

级别：stdout、error、warn、info、debug、trace。

何时使用 dora/logs，何时使用 send_logs_as：

dora/logssend_logs_as
作用域一次性覆盖所有节点每次一个节点
需要修改 YAML只有消费者每个源节点
新增节点无需修改连线必须更新消费者
使用场景仪表盘、监控按节点处理日志

完整可运行示例见 examples/log-aggregator/。

max_log_size

启用基于大小的日志文件轮转。

nodes:
  - id: sensor
    path: ./target/debug/sensor
    max_log_size: "50MB"
值字节
"1KB" 或 "1K"1,024
"50MB" 或 "50M"52,428,800
"1GB" 或 "1G"1,073,741,824
"1000"1,000（纯数字表示字节）

当活动日志文件超过配置的大小时，守护进程会：

  1. 刷新并关闭当前文件
  2. 重命名已有的轮转文件：.4.jsonl -> .5.jsonl、.3.jsonl -> .4.jsonl，依此类推。
  3. 重命名当前文件：log_sensor.jsonl -> log_sensor.1.jsonl
  4. 创建一个新的 log_sensor.jsonl
  5. 删除超出轮转限制的文件（默认 5 个，可通过 max_rotated_files 配置）

命名规则：

log_sensor.jsonl       # current (active)
log_sensor.1.jsonl     # previous
log_sensor.2.jsonl     # older
log_sensor.3.jsonl
log_sensor.4.jsonl
log_sensor.5.jsonl     # oldest (deleted on next rotation)

每个节点的最大磁盘占用：max_log_size * (1 + max_rotated_files)（1 个活动文件 + N 个轮转文件）。

如果不设置 max_log_size，日志文件会无限增长。对于长期运行的数据流，务必设置该项。

dora logs --local 命令会自动读取某个节点的所有轮转文件，并按时间顺序将它们合并（最早的轮转文件在前，当前文件在最后）。

max_rotated_files

控制保留多少个轮转日志文件（默认：5，范围：0-100）。

nodes:
  - id: sensor
    path: ./target/debug/sensor
    max_log_size: "50MB"
    max_rotated_files: 10    # keep 10 rotated files instead of 5

设置 max_rotated_files: 10 和 max_log_size: "50MB" 时，每个节点的最大磁盘占用为 50MB * 11 = 550MB。较低的值可以节省磁盘空间；较高的值可以保留更多历史记录。

将 max_rotated_files: 0 设置为完全不保留历史记录：活动日志会被直接轮转清除而不是重命名，因此每个节点的磁盘占用始终保持为一个 max_log_size 大小的文件。

运行时节点限制

一个运行时节点（operator: / operators:）恰好持有一个算子，因此其日志字段来自该算子：

nodes:
  - id: runtime-node
    operator:
      python: process.py
      send_logs_as: logs
      min_log_level: info
      max_log_size: "100MB"

当算子设置了 send_logs_as 时，输出名称会以算子 ID 作为前缀（例如，对于 id: op1 的算子，输出名为 op1/logs）。

节点日志 API

节点可以使用节点 API 以编程方式发出结构化日志消息。这与向 stdout 写入 JSON 格式的日志行等效——守护进程会以相同的方式解析它们。

Rust

#![allow(unused)]
fn main() {
use dora_node_api::DoraNode;
use std::collections::BTreeMap;

let (node, mut events) = DoraNode::init_from_env()?;

// General log with level string and optional target
node.log("info", "sensor initialized", Some("sensor::init"));

// Convenience methods (no target parameter)
node.log_error("connection failed");
node.log_warn("temperature elevated");
node.log_info("reading acquired");
node.log_debug("raw bytes received");
node.log_trace("entering loop iteration");

// Structured fields (key-value context preserved through send_logs_as)
let mut fields = BTreeMap::new();
fields.insert("sensor_id".to_string(), "temp-01".to_string());
fields.insert("reading".to_string(), "42.5".to_string());
node.log_with_fields("info", "reading acquired", None, Some(&fields));
}

level 参数接受 "error"、"warn"（或 "warning"）、"info"、"debug"、"trace"。未知级别默认视为 "info"。字段（序列化后）总大小上限为 60 KB，这能确保单条日志远低于守护进程每行 1 MiB 的限制。

Python

Python 节点有三种记录日志的方式，全部都会生成结构化日志条目：

from dora import Node
import logging

node = Node()

# Option 1: Python's logging module (recommended -- auto-bridged by Node())
logging.info("sensor initialized")
logging.warning("temperature elevated")
logging.debug("raw bytes: %s", data)

# Option 2: Explicit dora API with level string
node.log("info", "sensor initialized", target="sensor.init")
node.log("info", "reading acquired", fields={"sensor_id": "temp-01", "reading": "42.5"})

# Option 3: Convenience methods
node.log_error("connection failed")
node.log_warn("temperature elevated")
node.log_info("reading acquired")
node.log_debug("raw bytes received")
node.log_trace("entering loop iteration")

# This also works but produces "stdout"-level entries (no structure):
print("raw output")

Python 日志桥接的工作原理：创建 Node() 时，会安装一个自定义的 logging.Handler，把所有 Python logging 调用都通过 Rust 的 tracing 系统路由出去。守护进程会把这些调用解析为带级别、消息、文件路径和行号的结构化日志条目。这一过程自动完成——无需任何配置。

方法是否结构化？是否支持字段？适用场景
logging.info()是不支持（可用 extra= 实现自定义格式化）通用日志记录
node.log("info", msg, fields={...})是是需要结构化的键值对上下文时
node.log_info(msg)是否快捷的一行写法，等同于 node.log("info", msg)
print()不支持（stdout 级别）否旧代码、快速调试

常见陷阱：不要在创建 Node() 之前调用 logging.basicConfig()。节点构造函数会设置日志桥接；如果先调用 basicConfig()，可能会安装一个互相冲突的 handler。如果需要自定义格式化器，请在 Node() 创建之后再配置。

C

#include "node_api.h"

void *ctx = init_dora_context_from_env();
const char *level = "info";
const char *msg = "sensor initialized";
dora_log(ctx, level, strlen(level), msg, strlen(msg));

日志工具库（dora-log-utils）

dora-log-utils crate 提供了用于在自定义 sink 节点中处理 LogMessage 条目的解析、合并、过滤与格式化工具。当你要构建通过 send_logs_as 消费日志数据的节点时可以使用它。

API

#![allow(unused)]
fn main() {
use dora_log_utils;

// Parse a LogMessage from JSON (as received from send_logs_as)
let log = dora_log_utils::parse_log(json_str)?;

// Parse directly from Arrow input data (convenience for event handlers)
let log = dora_log_utils::parse_log_from_arrow(&data)?;

// Merge multiple log streams into a single timeline
let merged = dora_log_utils::merge_by_timestamp(vec![stream_a, stream_b]);

// Filter by minimum level
let errors = dora_log_utils::filter_by_level(&logs, &min_level);

// Format as JSON (one line, no trailing newline)
let json = dora_log_utils::format_json(&log);

// Format as compact single-line: "<timestamp> <node> <LEVEL>: <message>"
let compact = dora_log_utils::format_compact(&log);

// Format as pretty: "[<timestamp>][<LEVEL>][<node>] <message>"
let pretty = dora_log_utils::format_pretty(&log);
}

日志 Sink 示例

以下三个示例 sink 节点展示了如何消费通过 send_logs_as 路由来的日志，并把它们转发到外部目的地。

文件 Sink（examples/log-sink-file/）

把来自多个节点的日志流合并写入单个 JSONL 文件。适用于统一的日志收集。

nodes:
  - id: sensor
    path: sensor.py
    send_logs_as: log_entries
    inputs:
      tick: dora/timer/millis/200
    outputs:
      - reading
      - log_entries

  - id: processor
    path: processor.py
    send_logs_as: log_entries
    inputs:
      reading: sensor/reading
    outputs:
      - result
      - log_entries

  - id: file_sink
    path: log-sink-file

      sensor_logs: sensor/log_entries
      processor_logs: processor/log_entries

文件 sink 从环境变量读取 LOG_FILE（默认为 ./combined.jsonl），用 dora_log_utils::parse_log_from_arrow() 解析每条收到的 Arrow 消息，将其格式化为 JSON，并追加写入文件。

TCP Sink（examples/log-sink-tcp/）

把日志条目通过 TCP 套接字转发给远程日志收集器。适用于没有本地文件系统、需要把日志流式传输到设备外部的嵌入式系统。

nodes:
  - id: source
    path: source.py
    send_logs_as: log_entries
    inputs:
      tick: dora/timer/millis/500
    outputs:
      - data
      - log_entries

  - id: tcp_sink
    path: log-sink-tcp
    inputs:
      logs: source/log_entries
    env:
      SINK_ADDR: "127.0.0.1:9876"

TCP sink 从环境变量读取 SINK_ADDR（默认为 127.0.0.1:9876），启动时连接到服务器，并把每条日志作为一行 JSON 发送。写入失败时会自动重连。

告警路由器（examples/log-sink-alert/）

按严重级别拆分收到的日志条目。所有日志都会转发到 all_logs 输出；只有 error 和 warn 级别的日志才会转发到 alerts 输出。这样下游节点就能对告警进行不同处理（例如触发通知、写入专用文件）。

nodes:
  - id: source
    path: my_node.py
    send_stdout_as: log_entries
    inputs:
      tick: dora/timer/millis/200
    outputs:
      - log_entries

  - id: alert_router
    path: log-sink-alert
    inputs:
      logs: source/log_entries
    outputs:
      - all_logs
      - alerts

源节点使用 send_stdout_as 把自己的 stdout 行作为 Arrow 字符串数据路由出去。路由器用 dora_log_utils::parse_log_from_arrow() 解析每条日志，检查其级别，并用 node.send_output() 把数据转发到相应的输出。使用 node API 的节点也可以用 send_logs_as 来路由来自 node.log() 的结构化日志。

构建自定义 Sink

要构建自己的 sink 节点，请遵循以下模式：

use dora_node_api::{DoraNode, Event};

fn main() -> eyre::Result<()> {
    let (_node, mut events) = DoraNode::init_from_env()?;

    while let Some(event) = events.recv() {
        match event {
            Event::Input { data, .. } => {
                let log = dora_log_utils::parse_log_from_arrow(&data)?;
                // Process the log entry: write to file, send over network, etc.
                let json = dora_log_utils::format_json(&log);
                println!("{json}");
            }
            Event::Stop(_) => break,
            _ => {}
        }
    }
    Ok(())
}

守护进程处理日志的方式

了解其内部流水线有助于调试和调优。针对每个节点，守护进程都会运行一个专用的异步任务，按顺序处理各行日志：

Node Process (stdout/stderr)
    |
    v
[1] Capture: lines buffered in mpsc channel (capacity 100)
    |
    v
[2] send_stdout_as: raw line -> Arrow data -> dataflow output
    |
    v
[3] Parse: try JSON structured log, fall back to Stdout-level
    |
    v
[4] min_log_level filter: drop messages below threshold
    |
    v
[5] send_logs_as: LogMessage -> JSON -> Arrow data -> dataflow output
    |
    v
[6] Write JSONL: compact format to log file, track bytes written
    |
    v
[7] Rotation check: if bytes_written >= max_log_size, rotate files
    |
    v
[8] Forward: send LogMessage to display channel (unless DORA_QUIET)
    |
    v
[9] Sync: fsync log file to disk

关键细节：

  • 步骤 2 发生在解析之前，因此 send_stdout_as 会捕获每一行，包括非结构化输出
  • 步骤 4 发生在步骤 5——8 之前，因此 min_log_level 会抑制所有后续处理流程中的消息
  • 步骤 5 只在结构化日志成功解析时触发（即步骤 3 的成功路径）
  • 步骤 8 会发送到 flume 通道（dora run 直接模式）或协调器（分布式模式）
  • 步骤 9 在每次写入后都会调用 sync_all()，以一定的 I/O 开销为代价保证持久性

结构化日志解析

当节点输出 JSON 格式的日志（例如来自带 JSON 格式化的 tracing-subscriber）时，守护进程会提取：

  • level：日志严重级别
  • message：日志文本
  • target：模块路径
  • timestamp：日志发出的时间
  • fields：任意键值对
  • build_id、dataflow_id、node_id、daemon_id：作为回退，从字段中提取

守护进程还会在所有消息上设置 dataflow_id、node_id 和 daemon_id，以确保它们始终存在于日志文件中。

协调器日志流式传输协议

当守护进程在协调器之下运行（分布式模式）时，日志转发通过 WebSocket 进行：

  1. 守护进程 -> 协调器：每条 LogMessage 都会被包装进 DaemonEvent::Log(message)，并通过该守护进程的 WebSocket 连接发送
  2. 协调器存储：协调器存储/转发日志
  3. CLI 订阅：CLI 通过其 WebSocket 连接发送 ControlRequest::LogSubscribe { dataflow_id, level }
  4. 服务端过滤：协调器只转发满足 msg_level <= subscription_level 的消息。这可以减少被过滤订阅的网络流量
  5. CLI 接收：消息以序列化的 LogMessage 结构体形式到达

--level 标志映射到 log::LevelFilter：

  • stdout -> LevelFilter::Trace（最宽松，接收所有消息）
  • info -> LevelFilter::Info（接收 Error、Warn、Info）
  • 等等。

1. 调试一个日志噪音过多的传感器流水线

一个摄像头传感器节点让日志被大量 debug 消息淹没，导致很难看到其他节点的错误信息。

nodes:
  - id: camera
    path: ./target/debug/camera
    min_log_level: warn          # suppress info/debug/trace at the source
    max_log_size: "10MB"         # limit disk usage

  - id: detector
    path: ./target/debug/detector

  - id: planner
    path: ./target/debug/planner

# During development: see everything from detector, only warnings from camera
dora run dataflow.yml --log-level debug --log-filter "camera=warn,detector=debug"

# In production: only errors
export DORA_LOG_LEVEL=error
dora run dataflow.yml

会发生什么：

  • 摄像头节点的 debug/info 消息会在到达日志文件之前被守护进程丢弃（min_log_level: warn）
  • CLI 会基于 --log-filter 进一步过滤显示内容
  • 日志文件会在达到 10MB 时轮转，摄像头节点的日志在磁盘上最多保留 60MB

fn main() {
use dora_node_api::{DoraNode, Event};
use dora_message::common::{LogLevel, LogLevelOrStdout};

let (mut node, mut events) = DoraNode::init_from_env()?;
while let Some(event) = events.recv() {
    match event {
        Event::Input { data, .. } => {

                LogLevelOrStdout::LogLevel(LogLevel::Error));

            if is_error || log.message.contains("timeout") {
                // Send alert downstream
                node.send_output("alerts", /* ... */)?;
            }
        }
        Event::Stop(_) => break,
        _ => {}
    }
}
}

性能考量

日志记录会带来与日志量成正比的 I/O 开销。以下是调优方法：

min_log_level 是影响最大的设置。它会在守护进程处进行过滤，发生在任何 I/O 之前：不写日志文件、不转发给协调器、也不经过 send_logs_as 路由。一个以每秒 1000 条 debug 日志速率发出消息的节点，在 min_log_level: info 设置下，这些消息产生的开销为零。

send_logs_as 会为每行日志添加一条数据流消息。每条解析后的日志条目都会被序列化为 JSON、转换为 Arrow，并通过数据流发送。对于高频日志节点，这会消耗大量带宽。使用 min_log_level 来限制被路由的内容。

dora/logs 的多个订阅者共享同一份序列化结果。守护进程只会把每行日志转换为 Arrow 一次，然后为每个订阅者克隆该结果。开销随订阅者数量线性增长，而非“日志量 × 订阅者数量”。对于大多数数据流（1~3 个日志订阅者）而言，这一开销可忽略不计。

单行日志大小上限为 1 MB。来自节点 stdout/stderr 的超过 1 MB 的行会被截断，以防止堆内存耗尽。这可以防止存在缺陷的节点向 stdout 输出大量二进制数据。

建议为长期运行的数据流启用日志文件轮转。如果不设置 max_log_size，日志文件会无限增长。一个以每秒 100 行、每行约 200 字节输出的节点，大约 14 小时就能填满 1 GB。

生产环境推荐配置：

nodes:
  - id: my-node
    path: ./my-node
    min_log_level: info        # drop debug/trace at source
    max_log_size: "50MB"       # rotate at 50MB
    max_rotated_files: 5       # keep 5 rotated files (300MB max)

最佳实践

在生产环境中设置 min_log_level。在守护进程层面做源头过滤，可以防止调试噪音进入日志文件和网络。由于过滤发生在任何 I/O 之前，这是减少日志量最有效的方式。

为长期运行的数据流始终设置 max_log_size。如果没有轮转，单个噪音较多的节点就可能填满磁盘。建议从 "50MB" 开始（启用轮转后每个节点总计 300MB），并根据你的存储预算进行调整。使用 max_rotated_files 来调整保留多少历史文件（默认 5，范围 0~100）。

使用环境变量设置团队默认值。在 Shell 配置文件或 CI 配置中设置 DORA_LOG_LEVEL 和 DORA_LOG_FORMAT。个别开发者可以用 CLI 参数覆盖这些设置。

在开发过程中使用 --log-filter。无需修改 YAML 配置，可以使用按节点的显示覆盖项来聚焦正在调试的节点：--log-filter "my-node=debug"。

将 send_logs_as 用于运维监控。可以构建监控节点来检测错误模式、计算错误率或转发告警。这样可以把监控逻辑保留在数据流图内。可以使用 dora-log-utils 在自定义 sink 节点中解析和格式化日志条目（参见 examples/log-sink-file/ 和 examples/log-sink-tcp/）。

对于结构化数据，优先使用 send_logs_as 而非 send_stdout_as。send_stdout_as 会捕获每一行 stdout 输出（包括原始打印内容），而 send_logs_as 只捕获带有完整元数据的、已解析的结构化日志条目。

在事后调试时使用 --local。发生崩溃后，dora logs --local --all-nodes 无需运行中的协调器即可工作，并会将所有节点的日志按时间顺序合并。

结合 --since 和 --grep 进行有针对性的调试。不必在成千上万行中翻找，可以缩小范围：dora logs --local sensor --since 5m --grep "error"。

日志管道使用 JSON 格式。将日志提供给外部系统（ELK、Grafana Loki、Datadog）时，使用 --log-format json 以便进行结构化接入。
