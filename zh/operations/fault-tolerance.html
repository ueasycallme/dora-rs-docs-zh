Dora 用户指南

容错

Dora 为机器人和 AI 数据流提供了内置的容错能力。节点可以在失败时自动重启、检测过期的上游连接、在输入不可用时优雅降级，协调器还可以将状态持久化到磁盘，使其在崩溃和重启后依然存活。

功能概览

功能作用域配置
重启策略逐节点restart_policy, max_restarts, restart_delay, …
健康监控逐节点health_check_timeout、health_check_interval（数据流级别）
输入超时按输入input_timeout
断路器自动由 input_timeout 触发，自动恢复
NodeRestarted 事件下游节点上游重启时自动触发
InputTracker APIRust 节点dora_node_api::InputTracker
可观测性整个守护进程范围定期记录的原子计数器
分布式健康检查多守护进程协调器心跳监控
协调器状态持久化协调器--store redb（需要 redb-backend 功能特性）

重启策略

控制节点退出或崩溃时的行为。

配置

nodes:
  - id: my-node
    path: ./target/debug/my-node
    restart_policy: on-failure  # never | on-failure | always
    max_restarts: 5             # 0 = unlimited (default: 0)
    restart_delay: 1.0          # initial delay in seconds
    max_restart_delay: 30.0     # cap for exponential backoff
    restart_window: 300.0       # reset counter after this many seconds

策略类型

never（默认）——节点不会被重启。失败将正常传播。

on-failure——仅当节点以非零退出码退出时才重启。正常退出（退出码为 0）不会被重启。

always——任何退出都会重启，除非：

  • 数据流是被用户停止的（dora stop 或 Ctrl-C）
  • 所有输入都已关闭，且节点以非零退出码退出

重启在内部的工作方式

当一个节点进程退出时，守护进程按以下顺序评估重启决策：

  1. 策略检查：重启策略是否允许重启？
    • Never -> 不重启
    • OnFailure -> 仅当退出码 != 0 时重启
    • Always -> 重启
  2. 禁用检查：是否已设置 disable_restart？（在所有输入关闭或通过 stop_all 手动停止时会被设置）
  3. 窗口检查：如果设置了 restart_window，且自首次重启以来该窗口已过去，则将计数器重置为 0
  4. 限制检查：如果 max_restarts > 0 且窗口内计数器超过该值，则永久放弃
  5. 退避：如果设置了 restart_delay，则休眠计算出的延迟时间（唤醒后会重新检查 disable_restart）
  6. 重新启动：以相同的配置重新启动节点进程

守护进程在 spawn/prepared.rs 生命周期循环中按节点实例跟踪重启状态。每个节点运行在自己的 tokio 任务中，因此重启不会阻塞其他节点。

退避

当设置了 restart_delay 时，守护进程会在重启前等待。延迟时间在每次尝试时翻倍（指数退避），并受 max_restart_delay 限制。

退避指数在内部被限制为最多 16，以防止溢出（2^16 = 65536x multiplier）。

示例：restart_delay: 1.0 且 max_restart_delay: 10.0：

Attempt 1: wait 1s    (1.0 * 2^0)
Attempt 2: wait 2s    (1.0 * 2^1)
Attempt 3: wait 4s    (1.0 * 2^2)
Attempt 4: wait 8s    (1.0 * 2^3)
Attempt 5: wait 10s   (capped at max_restart_delay)
Attempt 6: wait 10s   (capped)

在退避休眠期间，守护进程会持续监控 disable_restart 标志。如果在节点等待重启期间所有输入都关闭了，重启将被取消，并记录日志信息：“restart cancelled: inputs closed during backoff wait”。

重启窗口

当设置了 restart_window 时，重启计数器会在窗口（从当前窗口的首次重启开始计算）过去后重置。这实现了“每 M 秒最多 N 次重启”的语义。

示例：max_restarts: 5、restart_window: 300.0 表示“每 5 分钟最多重启 5 次”。如果窗口期过去而未达到限制，计数器会重置，节点会获得另外 5 次尝试机会。

关闭期间禁用重启

当守护进程通过 stop_all 停止数据流时，会在发送 Stop 事件之前对每个节点调用 disable_restart()。这可以防止重启机制与关闭过程相互冲突。disable_restart 标志是一个在守护进程事件循环和节点的启动生命周期任务之间共享的 Arc<AtomicBool>。

NodeRestarted 事件

当一个节点重启时，守护进程会向所有消费其输出的下游节点发送 NodeRestarted 事件。这使下游节点可以：

  • 重置内部状态或缓存
  • 记录上游恢复的日志
  • 重新初始化连接或会话

该事件携带重启节点的 NodeId。下游节点会通过事件流自动收到该事件：

#![allow(unused)]
fn main() {
match event {
    Event::NodeRestarted { id } => {
        println!("upstream node {id} restarted, resetting state");
        // Clear any cached state from the old node instance
    }
    _ => {}
}
}

守护进程通过 dataflow.mappings 查找下游节点，该映射将每个节点的输出关联到所有订阅的 (receiver_node, input_id) 对。每次重启，每个唯一的接收方都会收到一次 NodeRestarted 事件。

健康监控

被动监控可以检测到停止与守护进程通信的挂起节点。

health_check_interval: 2.0  # seconds (default: 5.0, dataflow-level)
nodes:
  - id: my-node
    path: ./target/debug/my-node
    health_check_timeout: 30.0  # seconds (per-node)
    restart_policy: on-failure

可配置的健康检查间隔

health_check_interval 是一个数据流级别的设置，用于控制守护进程检查节点健康状态的频率。默认值为 5.0 秒。较小的值可以更快地检测到挂起的节点，但会增加更多开销。请在 dataflow YAML 的顶层设置此项，而非在单个节点下设置。

内部工作原理

守护进程会按配置的 health_check_interval 运行健康检查扫描（通过发出 Event::NodeHealthCheckInterval 的 tokio 定时流实现）。

每个 RunningNode 都有一个 last_activity: Arc<AtomicU64> 字段，用于存储最后一次通信的时间戳（自 epoch 起的毫秒数）。每当节点向守护进程发送任何请求（事件订阅、输出发送等）时，节点的通信处理器（node_communication/mod.rs）都会原子化地更新该字段。

健康检查函数（check_node_health）会遍历所有正在运行的节点：

  1. 跳过未设置 health_check_timeout 的节点
  2. 跳过尚未连接的节点（不在 connected_nodes 中）
  3. 计算 elapsed_ms = now - last_activity
  4. 若 elapsed_ms > timeout_ms，记录一条警告并杀死该节点进程

杀死后会执行正常的退出处理流程，从而评估重启策略。这意味着 health_check_timeout 配合 restart_policy: on-failure 可以自动恢复挂起的节点。

仅限连接建立后的存活检测

上面的第 2 步意味着 health_check_timeout 限定的是连接建立后的存活时间，而非总启动时间。节点首次订阅事件时（在 Node::init / DoraNode::init_from_env 内部）才会加入 connected_nodes，超时计时也只从那时起才开始生效。

这是有意为之：last_activity 的初始值为启动时间戳，若没有连接门控，节点正常的冷启动（如 Python 导入、模型权重加载）一旦超过 health_check_timeout，就会在启动过程中被 SIGKILLed——而在 restart_policy: always/on-failure 下，这会变成无法摆脱的重启循环。

代价是：若节点在订阅事件之前就已挂起——例如导入或初始化代码中的死锁，从未到达 Node::init——该看门狗不会回收它，数据流会一直处于待处理状态，等待这个节点。节点连接之前，正常的慢启动与挂起的启动是无法区分的，因此需要一个独立的启动截止时间来限定它们，而不是依赖这个超时。

何为“活动”

节点向守护进程发送的任何消息都算作活动：

  • 事件订阅请求
  • 输出数据发送（通过共享内存或 TCP）
  • 定时器滴答确认

从其他节点接收到的正常输入数据不会重置计时器——节点必须主动与守护进程通信。

输入超时与断路器

按输入设置的超时用于检测上游节点何时停止生成数据。

配置

nodes:
  - id: downstream-node
    path: ./target/debug/downstream
    inputs:
      sensor_data:
        source: camera-node/frames
        input_timeout: 5.0  # seconds

input_timeout 是按输入设置的，而非按节点设置。不同输入可以有不同的超时时间。

内部工作原理

守护进程为每个设有超时的输入维护一个 InputDeadline：

struct InputDeadline {
    timeout: Duration,        // configured timeout
    last_received: Instant,   // last time data arrived
}

这些信息存储在 RunningDataflow.input_deadlines 中，以 (NodeId, DataId) 为键。

超时检测在同一个 5 秒的健康检查周期内运行。check_input_timeouts 函数会：

  1. 扫描所有 input_deadlines 条目
  2. 若 last_received.elapsed() > timeout，则该输入被判定为“已损坏（broken）”
  3. (node_id, input_id) 这一对会从 input_deadlines 移动到 broken_inputs
  4. 守护进程调用 break_input()，向下游节点发送 InputClosed { id }
  5. 如果某节点的所有输入现在都已关闭（且没有已损坏/可恢复的），则会发送 AllInputsClosed，并禁用该节点的重启

截止时间重置：每当某个输入收到数据时，其 last_received 会被重置为 Instant::now()。

断路器：自动恢复

断路器通过 RunningDataflow.broken_inputs 跟踪已损坏的输入。当已损坏的输入上出现新数据时：

  1. 该数据正常传递给节点
  2. broken_inputs 中对应的条目会被移除
  3. 该输入会被重新加入 open_inputs
  4. 会创建一个新的 InputDeadline（重新开始计时）
  5. 会向该节点发送一个 InputRecovered { id } 事件
  6. circuit_breaker_recoveries 计数器会递增

这意味着恢复是完全自动的。如果上游节点（通过重启策略）重新启动并再次开始生成数据，下游节点会无缝地恢复接收。

节点侧的处理

在 Rust 节点中，应在事件循环里处理这些事件：

#![allow(unused)]
fn main() {
use dora_node_api::{DoraNode, Event};

let (mut node, mut events) = DoraNode::init_from_env()?;
while let Some(event) = events.recv() {
    match event {
        Event::Input { id, data, .. } => {
            // Normal processing
        }
        Event::InputClosed { id } => {
            // Upstream stopped producing on this input.
            // You can: use cached data, skip processing, alert operator, etc.
        }
        Event::InputRecovered { id } => {
            // Upstream is back online for this input.
            // Resume normal processing.
        }
        Event::Stop(_) => break,
        _ => {}
    }
}
}

InputTracker API（Rust）

InputTracker 辅助工具用于跟踪输入的健康状态，并为每个输入缓存最近一次收到的值，从而方便实现优雅降级。

#![allow(unused)]
fn main() {
use dora_node_api::{DoraNode, Event, InputTracker, InputState};

let (mut node, mut events) = DoraNode::init_from_env()?;
let mut tracker = InputTracker::new();

while let Some(event) = events.recv() {
    tracker.process_event(&event);

    match event {
        Event::Input { id, data, .. } => {
            // Fresh data available
        }
        Event::InputClosed { id } => {
            // Input timed out -- fall back to cached data
            if let Some(stale_data) = tracker.last_value(&id) {
                // Use stale_data as fallback
            }
        }
        Event::Stop(_) => break,
        _ => {}
    }

    // Check overall health
    if tracker.any_closed() {
        let closed: Vec<_> = tracker.closed_inputs();
        // Log or adjust behavior
    }
}
}

内部设计

InputTracker 维护两个 HashMap：

  • states: HashMap<DataId, InputState>——每个输入的当前状态（Healthy 或 Closed）
  • cache: HashMap<DataId, ArrowData>——每个输入最近一次收到的值

在 Event::Input 时，两个映射都会更新（state 设为 Healthy，cache 克隆数据）。在 Event::InputClosed 时，只有 state 会改变（cache 保持不变）。在 Event::InputRecovered 时，state 会被重新设为 Healthy。cache 永远不会被清空，因此即使输入关闭后，last_value() 仍始终返回最近一次的数据。

注意：ArrowData 包装了 Arc<dyn arrow::array::Array>，因此缓存克隆是引用计数的（开销很小）。

API 参考

方法返回描述
new()InputTracker创建一个空的 tracker
process_event(&Event)bool更新状态。如果事件相关则返回 true
state(&DataId)Option<InputState>当前状态（Healthy 或 Closed）
is_closed(&DataId)bool检查输入是否已关闭

可观测性

守护进程通过原子计数器（FaultToleranceStats）跟踪容错相关事件，并在每个 5 秒的健康检查周期中记录一次汇总日志。

计数器

计数器类型递增时机
restartsAtomicU64发起节点重启时（在启动生命周期中）
health_check_killsAtomicU64节点因无响应被健康检查杀死时
input_timeoutsAtomicU64输入超时触发（断路器跳闸）时
circuit_breaker_recoveriesAtomicU64已损坏的输入上到达数据（自动恢复）时

所有计数器都使用 Ordering::Relaxed，因为它们只是信息性的，不需要严格的顺序保证。

日志输出

当任意计数器非零时，守护进程会输出一条结构化日志：

INFO fault tolerance stats restarts=3 health_kills=0 input_timeouts=1 cb_recoveries=1

这些计数器在守护进程的整个生命周期内是累加的，不会在不同数据流之间重置。

分布式健康状态

在多守护进程部署中，协调器会监控各守护进程的心跳。

协议

  • 心跳间隔：3 秒（协调器向每个守护进程发送心跳）
  • 断线阈值：30 秒无响应
  • 检测：在每次心跳巡检时，协调器会移除在阈值时间内未响应的守护进程
  • 通知：协调器向所有剩余守护进程广播 PeerDaemonDisconnected { daemon_id }

DaemonInfo

ConnectedMachines CLI 查询返回 Vec<DaemonInfo>：

#![allow(unused)]
fn main() {
pub struct DaemonInfo {
    pub daemon_id: DaemonId,
    pub last_heartbeat_ago_ms: u64,  // milliseconds since last heartbeat
}
}

这使得监控工具能够检测到那些仍存活但响应缓慢的守护进程。

守护进程侧的处理

当守护进程收到 PeerDaemonDisconnected 时，会记录一条结构化警告：

WARN peer daemon disconnected daemon_id=machine-B

目前这仅是信息性的。未来的工作可能包括将节点自动迁移出已断开的守护进程。

协调器状态持久化

默认情况下，协调器将所有状态保存在内存中。如果协调器进程崩溃或被重启，所有正在运行的数据流信息都会丢失——守护进程会继续运行，但会变成孤立状态，用户必须手动重新运行数据流。

redb 存储后端通过使用 redb（一个纯 Rust 实现的嵌入式键值存储，采用天生具备崩溃安全性的写时复制 B 树）将协调器状态持久化到磁盘上的单个文件来解决这个问题。

设计：无状态协调器 + 有状态后端

协调器本身在 K8s 意义上仍然是无状态的——可以随时停止和重启。所有持久状态都保存在 CoordinatorStore trait 背后的存储后端中：

Coordinator (stateless process)
    |
    v
CoordinatorStore trait
    |
    +-- InMemoryStore (default, no persistence)
    +-- RedbStore     (persists to ~/.dora/coordinator.redb)

这种分离意味着：

  • 协调器事件循环在正常运行期间从不读取文件系统（仅在启动恢复时读取）
  • 所有状态变更都会在明确定义的持久化点写入存储
  • 存储可以在不更改协调器逻辑的情况下替换

启用持久化

# Use default path (~/.dora/coordinator.redb)
dora coordinator --store redb

# Use custom path
dora coordinator --store redb:/path/to/coordinator.redb

# Default: in-memory only (no persistence)
dora coordinator --store memory

redb 后端需要 redb-backend Cargo 特性，该特性在默认的 CLI 构建中已启用。

持久化内容

存储会跟踪三种记录类型：

记录类型键持久化字段
DataflowRecordUUID（16 字节）uuid、name、descriptor（JSON）、status、守护进程 ID、代计数（generation）、创建/更新时间戳
BuildRecordUUID（16 字节）构建 ID、status、错误信息、创建/更新时间戳
DaemonInfoDaemonId（postcard）守护进程 ID、机器 ID

记录使用 postcard 进行序列化，以实现紧凑且快速的编码。

数据流状态生命周期

协调器在每次状态转换时都会持久化数据流状态：

Start command     -->  Pending
All daemons ready -->  Running
Stop command      -->  Stopping
All nodes finish  -->  Succeeded  or  Failed { error }
Spawn failure     -->  Failed { error: "spawn failed: ..." }

每次持久化调用都会使记录的 generation 计数器递增，从而提供用于冲突检测的单调版本号。

持久化时机

协调器会在事件循环中的以下时刻写入存储：

  1. 数据流启动（ControlRequest::Start）——创建状态为 Pending 的记录
  2. 数据流已启动（所有守护进程返回成功的 DataflowSpawnResult）——更新为 Running
  3. 启动失败（DataflowSpawnResult 返回错误）——更新为 Failed，并附带实际错误信息
  4. 请求停止（ControlRequest::Stop 或 StopByName）——更新为 Stopping
  5. 所有节点已结束（DataflowFinishedOnDaemon）——更新为 Succeeded 或 Failed，并附带各节点的错误详情
  6. 优雅关闭（Ctrl-C 或 Destroy 命令）——在发送停止消息之前，所有正在运行的数据流都标记为 Stopping

如果存储写入失败，协调器会记录一条警告并继续以内存状态运行。这可以防止存储故障阻塞数据流生命周期。

启动恢复

当协调器以包含上一次运行数据的 redb 存储启动时，会执行恢复操作：

  1. 通过 store.list_dataflows() 读取所有已持久化的数据流记录
  2. 对于任何处于非终止状态（Pending、Running、Stopping）的记录：
    • 将其标记为 Failed { error: "coordinator restarted" }
    • 递增代计数（generation）
    • 将更新后的记录写回存储
  3. 终止状态的记录（Succeeded、Failed）保持不变

这确保了来自已崩溃协调器的过期数据流不会与正在实际运行的数据流混淆。那些正在运行这些数据流的守护进程会独立检测到与协调器的连接断开。

错误详情保留

当数据流失败时，Failed 状态会包含实际的各节点错误信息，而不是一个通用的字符串：

Failed { error: "node-1: exited with code 137; node-2: failed to spawn node: binary not found" }

错误信息从所有守护进程的 DataflowDaemonResult.node_results 中收集，格式化为 node_id: error_message，并用 ; 连接。

模式版本管理

redb 数据库包含一个带有 schema_version 键的 meta 表。打开时：

  • 如果不存在版本号（全新的数据库），则写入当前版本号
  • 如果存储的版本号与二进制文件的版本号一致，数据库正常打开
  • 如果存在不一致，数据库会被拒绝打开并报错

这可以防止存储记录的序列化格式在 Dora 版本之间发生变化时出现静默数据损坏。当前的 schema 版本是 1。

文件安全

在 Unix 系统上：

  • 数据库文件在创建后会被设置为 0600（仅所有者可读写）
  • 默认目录（~/.dora/）被设置为 0700（仅所有者）
  • 通过 redb:/path 提供的自定义路径会经过校验，拒绝包含 .. 的路径片段

内部架构

#![allow(unused)]
fn main() {
// Store trait (libraries/coordinator-store/src/lib.rs)
pub trait CoordinatorStore: Send + Sync {
    fn put_dataflow(&self, record: &DataflowRecord) -> Result<()>;
    fn get_dataflow(&self, uuid: &Uuid) -> Result<Option<DataflowRecord>>;
    fn list_dataflows(&self) -> Result<Vec<DataflowRecord>>;
    fn delete_dataflow(&self, uuid: &Uuid) -> Result<()>;
    // ... daemon and build methods
}
}

RedbStore 实现使用三个 redb 表（daemons、dataflows、builds），采用基于 UUID 的二进制键和 postcard 序列化的值。所有操作都是同步的（redb 是一个同步库）；协调器直接从异步事件循环中调用它们，因为这些是快速的进程内操作。

编码和解码两端都对称地强制执行 64 MiB 的记录大小限制，因此永远不会写入一条读取方随后会拒绝的记录。postcard 只从传入的切片中读取，不会根据长度前缀预先分配内存，因此损坏的行不会导致大规模内存分配。

使用场景

1. 存在间歇性硬件故障的相机流水线

相机驱动节点偶尔会因为 USB 断连而崩溃。处理流水线应当能挺过这些中断，并在相机重新连接后恢复。

nodes:
  - id: camera-driver
    path: ./target/debug/camera-driver
    restart_policy: on-failure
    max_restarts: 0               # unlimited -- hardware failures are expected
    restart_delay: 2.0            # wait for USB to re-enumerate
    max_restart_delay: 30.0
    inputs:
      tick: dora/timer/millis/33  # ~30 FPS
    outputs:
      - frames

  - id: object-detector
    path: ./target/debug/detector
    inputs:
      frames:
        source: camera-driver/frames
        input_timeout: 5.0        # tolerate 5s camera outage
    outputs:
      - detections

  - id: planner
    path: ./target/debug/planner
    inputs:
      detections:
        source: object-detector/detections
        input_timeout: 10.0       # longer tolerance -- can plan with stale data
      lidar:
        source: lidar-driver/points
        input_timeout: 3.0

相机崩溃时发生的情况：

  1. camera-driver 以非零退出码退出
  2. 守护进程评估 on-failure 策略 -> 退避 2 秒后重启
  3. 在中断期间，object-detector 在 5 秒后收到 InputClosed { id: "frames" }
  4. planner 在 10 秒后收到 InputClosed { id: "detections" }
  5. 相机重启，开始产生帧
  6. object-detector 收到新的帧数据以及 InputRecovered { id: "frames" }（断路器恢复）
  7. planner 收到检测结果以及 InputRecovered { id: "detections" }

planner 中的节点端处理：

#![allow(unused)]
fn main() {
use dora_node_api::{DoraNode, Event, InputTracker};

let (mut node, mut events) = DoraNode::init_from_env()?;
let mut tracker = InputTracker::new();

while let Some(event) = events.recv() {
    tracker.process_event(&event);

    match event {
        Event::Input { id, data, .. } => match id.as_ref() {
            "detections" => plan_with_detections(&data),
            "lidar" => update_lidar_map(&data),
            _ => {}
        },
        Event::InputClosed { id } => match id.as_ref() {
            "detections" => {
                // Camera pipeline down -- plan with lidar only
                plan_lidar_only();
            }
            "lidar" => {
                // LiDAR down -- use last known detection data
                if let Some(stale) = tracker.last_value(&"detections".into()) {
                    plan_with_stale_detections(stale);
                }
            }
            _ => {}
        },
        Event::Stop(_) => break,
        _ => {}
    }
}
}

2. 存在 OOM 崩溃的 ML 推理节点

ML 推理节点在处理大输入时偶尔会耗尽内存。它应该快速重启，但在反复失败后放弃（这表明存在系统性问题）。

nodes:
  - id: ml-inference
    path: ./target/debug/ml-inference
    restart_policy: on-failure
    max_restarts: 3
    restart_delay: 0.5
    restart_window: 60.0          # 3 restarts per minute
    health_check_timeout: 60.0    # ML inference can be slow
    inputs:
      images:
        source: preprocessor/images
    outputs:
      - predictions

行为：

  • 节点因 OOM 崩溃 -> 0.5 秒后重启
  • 在另一个大输入上再次崩溃 -> 1.0 秒后重启
  • 第三次崩溃 -> 2.0 秒后重启
  • 60 秒内第四次崩溃 -> 超过 max_restarts，节点永久失败
  • 如果节点在第一次崩溃后稳定运行 60 秒，重启窗口会重置，它会再获得 3 次机会

3. 具有优雅降级能力的多传感器融合

一台机器人融合了来自多个传感器的数据。单个传感器可能会失效，但系统应当以降低的能力继续运行。

nodes:
  - id: sensor-fusion
    path: ./target/debug/sensor-fusion
    inputs:
      camera:
        source: camera-node/frames
        input_timeout: 3.0
      lidar:
        source: lidar-node/points
        input_timeout: 3.0
      imu:
        source: imu-node/readings
        input_timeout: 1.0        # IMU is critical, short timeout
      gps:
        source: gps-node/fix
        input_timeout: 10.0       # GPS can be intermittent
    outputs:
      - fused-state

使用 InputTracker 的节点端：

#![allow(unused)]
fn main() {
use dora_node_api::{DoraNode, Event, InputTracker};

let (mut node, mut events) = DoraNode::init_from_env()?;
let mut tracker = InputTracker::new();

while let Some(event) = events.recv() {
    tracker.process_event(&event);

    match event {
        Event::Input { id, data, .. } => {
            // Process fresh data from any sensor
            update_sensor(&id, &data);
            compute_and_send_fusion(&mut node, &tracker);
        }
        Event::InputClosed { id } => {
            // Sensor went offline -- adjust fusion weights
            eprintln!("sensor {id} offline, degrading");
            compute_and_send_fusion(&mut node, &tracker);
        }
        Event::InputRecovered { id } => {
            // Sensor back online
            eprintln!("sensor {id} recovered");
        }
        Event::Stop(_) => break,
        _ => {}
    }
}

fn compute_and_send_fusion(node: &mut DoraNode, tracker: &InputTracker) {
    // Use fresh data where available, stale cache for degraded sensors
    let camera = tracker.last_value(&"camera".into());
    let lidar = tracker.last_value(&"lidar".into());
    let imu = tracker.last_value(&"imu".into());

    if tracker.is_closed(&"imu".into()) {
        // IMU is critical -- switch to emergency mode
        emergency_stop(node);
        return;
    }

    // Fuse available sensors, weighting active ones higher
    let closed = tracker.closed_inputs();
    let active_count = 4 - closed.len();
    // ... fusion logic using active_count for confidence weighting
}
}

4. 长时间运行的数据处理流水线

批处理流水线持续运行。处理节点偶尔会由于第三方库的 bug 而挂起。健康监控会检测并从这些挂起中恢复。

nodes:
  - id: data-ingest
    path: ./target/debug/ingest
    restart_policy: always        # always restart -- this is a long-running service
    max_restarts: 0               # unlimited
    restart_delay: 1.0
    inputs:
      tick: dora/timer/millis/1000
    outputs:
      - records

  - id: processor
    path: ./target/debug/processor
    restart_policy: on-failure
    max_restarts: 10
    restart_delay: 0.5
    restart_window: 600.0         # 10 restarts per 10 minutes
    health_check_timeout: 30.0    # kill if hung for 30s
    inputs:
      records: data-ingest/records
    outputs:
      - results

  - id: writer
    path: ./target/debug/writer
    restart_policy: on-failure
    max_restarts: 5
    restart_delay: 2.0            # give DB time to recover
    max_restart_delay: 60.0
    inputs:
      results:
        source: processor/results
        input_timeout: 60.0       # processor may be slow

处理器挂起时发生的情况：

  1. 处理器停止与守护进程通信
  2. 30 秒后，健康检查检测到挂起并终止该进程
  3. health_check_kills 计数器递增
  4. 守护进程评估 on-failure -> 0.5 秒后重启
  5. 新的处理器实例启动，从 data-ingest 恢复消费
  6. writer 可能在 60 秒超时期间收到了 InputClosed——如果重启足够快，也可能没有收到
  7. 如果 writer 确实收到了 InputClosed，当新结果到达时它会收到 InputRecovered

5. 带有守护进程故障检测的分布式部署

一个多机器部署，协调器监控守护进程的健康状态。

Machine A (coordinator + daemon):  camera-driver, preprocessor
Machine B (daemon):                ml-inference, postprocessor
Machine C (daemon):                planner, actuator-driver

机器 B 失去网络连接时发生的情况：

  1. 协调器对机器 B 的心跳失败
  2. 30 秒没有响应后，协调器将机器 B 从活跃守护进程中移除
  3. 协调器向机器 A 和机器 C 广播 PeerDaemonDisconnected { daemon_id: "machine-B" }
  4. A 和 C 上的守护进程记录日志：WARN peer daemon disconnected daemon_id=machine-B
  5. A 和 C 上接收来自机器 B 节点输入的节点会收到 InputClosed 事件（通过它们的输入超时）
  6. 对 ConnectedMachines 的 CLI 查询只显示 A 和 C，以及它们的 last_heartbeat_ago_ms

6. 使用 redb 持久化的协调器崩溃恢复

一个长时间运行的多守护进程部署，协调器必须在重启后不丢失数据流历史记录。

# Start coordinator with persistent store
dora coordinator --store redb

# In another terminal, start a dataflow
dora start examples/rust-dataflow/dataflow.yml --name my-pipeline --detach

# Coordinator crashes or is killed (e.g., OOM, hardware failure)
# ... time passes ...

# Restart coordinator with the same store
dora coordinator --store redb

重启时发生的情况：

  1. 协调器打开 ~/.dora/coordinator.redb 并读取持久化的数据流记录
  2. 发现 my-pipeline 状态为 Running
  3. 将其标记为 Failed { error: "coordinator restarted" }，并递增 generation
  4. 记录日志：INFO recovering stale dataflow <uuid> ("my-pipeline") -> marking as Failed
  5. dora list 现在会显示 my-pipeline 及其最终状态和时间戳
  6. 各守护进程独立检测到协调器断开连接，并停止它们的节点
  7. 用户可以启动新的数据流——协调器完全可以正常工作

关键优势在于：协调器在重启之间保留了数据流生命周期事件的完整历史记录。如果没有 --store redb，所有状态都会丢失，操作员将无法得知崩溃前正在运行什么。

7. 始终重启的周期性批处理作业

一个处理批次并在完成后退出的节点。它应该重启以处理下一个批次。

nodes:
  - id: batch-processor
    path: ./target/debug/batch-proc
    restart_policy: always        # restart even on clean exit
    max_restarts: 0               # unlimited
    restart_delay: 10.0           # wait 10s between batches
    max_restart_delay: 10.0       # no exponential growth
    inputs:
      trigger: dora/timer/millis/1  # immediate first trigger
    outputs:
      - batch-result

该节点处理一个批次后以状态码 0 退出，等待 10 秒，然后重启处理下一个批次。always 策略即使在成功退出时也会确保重启。设置 restart_delay == max_restart_delay 可实现固定延迟。

最佳实践

从 on-failure 开始。仅对预期会退出并重启的节点（例如周期性批处理任务）使用 always。

设置 max_restarts。无限重启可能掩盖 bug。先从 3 到 5 开始，必要时再增加。仅对崩溃是预期且不可避免的节点（硬件驱动、外部 API 客户端）使用 max_restarts: 0。

使用 restart_window。可防止永久性重启循环。常用窗口为 60 到 300 秒。如果没有设置窗口，一个在启动时崩溃的节点会立即耗尽其重启预算。

调整 restart_delay。先从 0.5 到 1.0 秒开始。过短会导致抖动；过长会延迟恢复。应根据节点的典型启动时间以及故障的根本原因来匹配延迟：

  • USB/硬件重新连接：2 到 5 秒
  • 网络服务重新连接：1 到 3 秒
  • OOM/瞬时性 bug：0.5 到 1.0 秒

宽松设置 health_check_timeout。应至少为节点最长预期处理时间的 2 到 3 倍。ML 推理节点可能需要 60 秒以上。如果设置过短，健康的节点会在正常处理过程中被杀死。

为每个输入设置 input_timeout。并非所有输入都需要相同的超时时间。对高频输入（IMU、摄像头）使用较短的超时，对缓慢/突发性来源（GPS、批处理结果）使用较长的超时。一个好的起点是预期发布间隔的 3 到 5 倍。

在关键路径上使用 InputTracker。当一个节点必须在输入数据降质的情况下仍继续运行时，使用 InputTracker 回退到缓存数据。这对传感器融合、规划和控制节点至关重要。

在生产部署中使用 --store redb。redb 后端可确保协调器在崩溃和重启后仍保留数据流历史记录。默认的内存方式适合开发使用，但退出时会丢失所有状态。redb 文件很小（与数据流记录的数量成正比），开销可忽略不计。

已知限制：当协调器断开连接时，守护进程目前会在重新连接之前杀死正在运行的节点进程（#1799）。数据流记录在协调器重启后仍能保留（通过 redb），但正在运行的进程会从头重启。目前正在规划实现跨重连的无缝进程接管（参见 docs/plan-coordinator-ha.md 第 1.4 阶段）。

组合使用多个特性以实现纵深防御：

  • restart_policy + restart_delay -> 从节点崩溃中恢复
  • health_check_timeout -> 从挂起的节点中恢复
  • input_timeout -> 检测过期的上游数据
  • InputTracker -> 在节点代码中实现优雅降级
  • --store redb -> 在协调器崩溃后仍能存活
