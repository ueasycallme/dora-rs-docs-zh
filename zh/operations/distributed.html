分布式部署指南

dora 支持跨多台机器部署数据流，适用于多机器人编队、边缘 AI 流水线和分布式机器人系统。本指南涵盖集群管理、节点调度、二进制分发、自动恢复和运维最佳实践。

概述

dora 的分布式架构分为三层：

CLI  -->  Coordinator  -->  Daemon(s)  -->  Nodes / Operators
              (one)          (per machine)     (user code)
  • CLI 向协调器发送控制命令（build、start、stop）。
  • 协调器负责编排守护进程、解析节点放置位置，并管理数据流的生命周期。
  • 守护进程在每台机器上运行，负责启动并监管节点进程。
  • 节点之间通过共享内存（同一台机器）或 Zenoh 发布—订阅（跨机器）进行通信。

实现分布式部署有两种方式：

临时方式（Ad-hoc）——在每台机器上手动启动 dora daemon，再使用协调器进行控制。适合开发和测试。参见 CLI 参考中的分布式部署。

托管方式（cluster.yml）——在 YAML 文件中定义集群拓扑，再使用 dora cluster 命令通过 SSH 进行生命周期管理。本指南重点介绍托管方式。

快速开始

  1. 创建一个 cluster.yml：
coordinator:
  addr: 10.0.0.1
machines:
  - id: robot
    host: 10.0.0.2
    user: ubuntu
  - id: gpu-server
    host: 10.0.0.3
    user: ubuntu
  1. 启动集群：
dora cluster up cluster.yml
  1. 启动一个数据流：
dora start dataflow.yml --name my-app --attach
  1. 检查集群健康状态：
dora cluster status
  1. 拆除集群：
dora cluster down

集群配置参考

cluster.yml 文件定义了协调器地址以及集群中的机器集合。

完整模式

coordinator:
  addr: 10.0.0.1            # IP address the coordinator binds to (required)
  port: 6013                 # WebSocket port (default: 6013)

machines:
  - id: edge-01              # Unique machine identifier (required)
    host: 10.0.0.2           # SSH-reachable hostname or IP (required)
    user: ubuntu              # SSH user (optional, defaults to current user)
    labels:                   # Key-value labels for scheduling (optional)
      gpu: "true"
      arch: arm64

  - id: edge-02
    host: 10.0.0.3
    labels:
      arch: arm64

字段

coordinator

字段类型默认值描述
addrIP 地址（必填）协调器绑定的地址
portu166013WebSocket 端口

machines[]

字段类型默认值描述
idstring（必填）唯一的机器标识符，用于 deploy.machine
hoststring（必填）可通过 SSH 访问的主机名或 IP 地址
userstring当前用户SSH 用户名
labels映射空用于基于标签调度的键值对

验证规则

  • 必须至少定义一台机器。
  • 机器 ID 必须非空且唯一。
  • 机器的 host 必须非空。
  • 未知字段会被拒绝（deny_unknown_fields）。

示例：3 台机器的 GPU 集群

coordinator:
  addr: 192.168.1.1

machines:
  - id: coordinator-host
    host: 192.168.1.1
    labels:
      role: control

  - id: gpu-a100
    host: 192.168.1.10
    user: ml
    labels:
      gpu: a100
      arch: x86_64

  - id: jetson-01
    host: 192.168.1.20
    user: nvidia
    labels:
      gpu: jetson
      arch: arm64

集群命令参考

所有 dora cluster 命令都基于 cluster.yml 文件，并通过 SSH 来管理远程机器。

所用的 SSH 选项：BatchMode=yes、ConnectTimeout=10、StrictHostKeyChecking=accept-new。

dora cluster up

根据 cluster.yml 文件启动一个多机器集群。先在本地启动协调器，再通过 SSH 登录到每台机器启动守护进程。

dora cluster up <PATH>

参数：

参数描述
PATH集群配置文件的路径

行为：

  1. 加载并校验集群配置。
  2. 在本地的 addr:port 上启动协调器。
  3. 对每台机器，通过 SSH 登录并运行 nohup dora daemon --machine-id <id> --coordinator-addr <addr> --coordinator-port <port> [--labels k1=v1,k2=v2] --quiet。
  4. 持续轮询，直到所有预期的守护进程都向协调器注册完成（30 秒超时）。

示例：

$ dora cluster up cluster.yml
Starting coordinator on 10.0.0.1:6013...
Starting daemon on robot (ubuntu@10.0.0.2)... OK
Starting daemon on gpu-server (ubuntu@10.0.0.3)... OK
All 2 daemons connected.

dora cluster status

显示集群当前的状态，展示已连接的守护进程以及活跃的数据流数量。

dora cluster status [--coordinator-addr ADDR] [--coordinator-port PORT]

标志：

标志默认值描述
--coordinator-addrlocalhost协调器的主机名或 IP 地址
--coordinator-port6013协调器 WebSocket 端口

示例：

$ dora cluster status
DAEMON ID      LAST HEARTBEAT
robot          2s ago
gpu-server     1s ago

Active dataflows: 1

dora cluster down

拆除集群（协调器及所有守护进程）。

dora cluster down [--coordinator-addr ADDR] [--coordinator-port PORT]

终止所有守护进程以及协调器进程。

dora cluster install

在每台机器上以 systemd 服务的形式安装 dora-daemon。通过 SSH 登录到每台机器，写入 systemd unit 文件，并启用该服务。

dora cluster install <PATH>

参数：

参数描述
PATH集群配置文件的路径

行为：

对每台机器，创建并启用名为 dora-daemon-<id> 的 systemd 服务。该 unit 文件：

[Unit]
Description=Dora Daemon (<id>)
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=dora daemon --machine-id <id> --coordinator-addr <addr> --coordinator-port <port> --labels k1=v1,k2=v2 --quiet
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

示例：

$ dora cluster install cluster.yml
Installing dora-daemon-robot on ubuntu@10.0.0.2... OK
Installing dora-daemon-gpu-server on ubuntu@10.0.0.3... OK
2/2 succeeded.

dora cluster uninstall

从每台机器上卸载 dora-daemon 的 systemd 服务。停止、禁用并移除该 systemd unit。

dora cluster uninstall <PATH>

行为：

对每台机器，运行：

sudo systemctl stop dora-daemon-<id>
sudo systemctl disable dora-daemon-<id>
sudo rm -f /etc/systemd/system/dora-daemon-<id>.service
sudo systemctl daemon-reload

dora cluster upgrade

滚动升级：将本地的 dora 二进制文件通过 SCP 复制到每台机器并重启守护进程。各机器依次处理，以保持可用性。

dora cluster upgrade <PATH>

行为：

对每台机器依次执行：

  1. 通过 SCP 将本地的 dora 二进制文件复制到目标机器的 /usr/local/bin/dora。
  2. 通过 sudo systemctl restart dora-daemon-<id> 重启该 systemd 服务。
  3. 轮询协调器，直到该守护进程重新连接（30 秒超时，每 500 毫秒轮询一次）。

在某台机器升级期间，其他机器上的节点会继续保持运行。

示例：

$ dora cluster upgrade cluster.yml
Upgrading robot (ubuntu@10.0.0.2)...
  SCP binary... OK
  Restart service... OK
  Waiting for reconnect... OK (3.2s)
Upgrading gpu-server (ubuntu@10.0.0.3)...
  SCP binary... OK
  Restart service... OK
  Waiting for reconnect... OK (2.8s)
2/2 succeeded.

dora cluster restart

按名称或 UUID 重启正在运行的数据流。会停止该数据流，并立即使用已保存的描述文件重新启动它（无需提供 YAML 路径）。

dora cluster restart <DATAFLOW>

参数：

参数描述
DATAFLOW要重启的数据流的名称或 UUID

示例：

$ dora cluster restart my-app
Restarting dataflow `my-app`
dataflow restarted: a1b2c3d4-... -> e5f6a7b8-...

节点调度

协调器收到数据流时，会根据 dataflow YAML 中的 deploy 部分，决定由哪个守护进程运行每个节点。解析优先级为：machine > labels > unnamed。

基于机器的调度

通过 cluster.yml 中的 id，将某个节点分配到指定机器：

nodes:
  - id: camera
    deploy:
      machine: robot
    path: ./camera-driver
    outputs:
      - frames

协调器会查找 machine-id 相匹配的守护进程。如果没有匹配的守护进程处于连接状态，部署将失败，并提示：no matching daemon for machine id "robot"。

基于标签的调度

通过要求目标守护进程具备特定标签来分配节点：

nodes:
  - id: inference
    deploy:
      labels:
        gpu: "true"
    path: ./ml-model
    inputs:
      frames: camera/frames
    outputs:
      - predictions

协调器会找到第一个其标签超集包含所需标签的已连接守护进程。所有必需的键值对都必须精确匹配。如果没有守护进程满足要求，部署将失败，并提示：no daemon matches labels {"gpu": "true"}。

未指定的节点

没有 deploy 部分（或该部分为空）的节点会被分配给第一个未命名的守护进程——即在连接时未带 --machine-id 标志的守护进程。

resolve_daemon() 内部工作原理

协调器在 coordinator/run/mod.rs 中解析节点的放置位置：

resolve_daemon(connections, deploy) -> DaemonId
  1. If deploy.machine is Some(id):
       -> look up daemon by machine-id
  2. Else if deploy.labels is non-empty:
       -> find first daemon where all required labels match
  3. Else:
       -> pick first unnamed daemon

标签匹配函数会遍历所有已连接的守护进程，检查所需的每个键值对是否都存在于该守护进程的标签集合中（conn.labels.get(k) == Some(v)）。这是一种超集检查：拥有 {gpu: "true", arch: "arm64", role: "edge"} 的守护进程可以满足 {gpu: "true"} 的要求。

二进制分发

通过 distribute 字段控制节点二进制文件如何分发到远程守护进程。

Local（默认）

每个守护进程都在自己的机器上从源码构建。这是当前的默认行为。

nodes:
  - id: my-node
    deploy:
      machine: edge-01
      distribute: local
    path: ./my-node

SCP 模式

CLI 会在启动前通过 SSH/SCP 将本地构建的二进制文件推送到目标机器。

nodes:
  - id: my-node
    deploy:
      machine: edge-01
      distribute: scp
    path: ./my-node

HTTP 模式

协调器运行一个构件存储（artifact store）。守护进程在启动前通过 HTTP 从协调器拉取二进制文件。

nodes:
  - id: my-node
    deploy:
      machine: edge-01
      distribute: http
    path: ./my-node

构件通过协调器 WebSocket 端口上的 GET /api/artifacts/{build_id}/{node_id} 提供。该端点需要身份验证（Bearer token），并会对节点 ID 进行清理以防止路径遍历攻击。

各策略的适用场景

策略最适用于权衡
local同构集群、CI 构建需要在每台机器上都安装构建工具链
scp异构集群、交叉编译的二进制文件需要 CLI 对所有机器具有 SSH 访问权限
http隔离网络（air-gapped）的守护进程、防火墙隔离的网络需要所有守护进程都能访问到协调器

systemd 服务管理

在生产部署中，应将守护进程安装为 systemd 服务，使其能在重启后存活，并在失败时自动重启。

安装

dora cluster install cluster.yml

在每台机器上创建一个 systemd unit 文件（完整的 unit 模板见 dora cluster install）。关键属性：

  • Restart=on-failure 配合 RestartSec=5：守护进程崩溃时会自动重启。
  • After=network-online.target：启动前等待网络就绪。
  • WantedBy=multi-user.target：开机启动。

卸载

dora cluster uninstall cluster.yml

在每台机器上停止、禁用并移除 unit 文件，然后重新加载 systemd 守护进程。

验证服务状态

安装完成后，可直接检查服务状态：

ssh ubuntu@10.0.0.2 sudo systemctl status dora-daemon-robot

自动恢复

当守护进程断开连接并重新连接时（例如网络抖动、机器重启或服务重启之后），协调器会自动在该守护进程上重新启动所有缺失的数据流。

工作原理

  1. 守护进程重新连接，并发送一个 StatusReport，列出其当前正在运行的数据流。
  2. 协调器将该报告与其预期状态（该守护进程上应有节点的数据流）进行比较。
  3. 对于分配给该守护进程但守护进程未在报告中列出的每个正在运行的数据流节点，协调器会发送 SpawnDataflowNodes 命令以重新启动缺失的节点。

30 秒退避

为防止崩溃循环（例如节点一启动就立即崩溃），恢复机制采用按守护进程、按数据流的退避策略：

  • 每次尝试恢复后，协调器都会记录时间戳。
  • 在 30 秒内，针对同一守护进程 / 数据流组合的后续恢复操作将被跳过。
  • 当守护进程再次报告该数据流正在运行时，退避状态会被清除。

这意味着立即崩溃的节点每 30 秒最多只会被重新启动一次，而不会陷入紧密的循环。

限制

  • 自动恢复仅适用于通过 dora start 启动的数据流（由协调器管理）。本地通过 dora run 启动的数据流不会被协调器跟踪。
  • 恢复操作会重新启动分配给重新连接的守护进程的所有节点，而不是单个节点。如需在崩溃时按节点重启，请使用 重启策略。
  • 已知问题（#1799）：当守护进程与协调器之间的 WebSocket 连接断开时，守护进程目前会在重新连接之前终止所有正在运行的节点进程。这意味着协调器的自动恢复流程会从头重新启动节点，而不是复用仍在运行的进程。其净效果是短暂的中断（节点重启），而非无缝的连续性。目前计划修复此问题，以便在重连周期中保留正在运行的进程（参见 docs/plan-coordinator-ha.md 第 1.4 阶段）。

滚动升级

通过逐机器依次升级，在所有集群机器上以零停机方式升级 dora 二进制文件。

流程

dora cluster upgrade cluster.yml

对每台机器依次执行：

  1. 使用 SCP 将本地的 dora 二进制文件传输到目标机器的 /usr/local/bin/dora。
  2. 重启 systemd 服务（systemctl restart dora-daemon-<id>）。
  3. 轮询协调器，直到守护进程重新连接（超时时间 30 秒）。

由于机器是逐一升级的，其他机器上的节点会继续运行。守护进程重新连接后，自动恢复机制会重新启动该机器上原本运行的所有数据流节点。

前置条件

  • 守护进程必须以 systemd 服务的形式安装（dora cluster install）。
  • 本地的 dora 二进制文件必须与集群的协调器版本兼容。
  • 对所有目标机器拥有具备 sudo 权限的 SSH 访问能力。

使用场景

1. 边缘 AI 流水线（机器人 + GPU 服务器）

一个摄像头节点运行在机器人上，将帧发送到 GPU 服务器进行推理，推理结果再回传给机器人上的执行器。

cluster.yml：

coordinator:
  addr: 192.168.1.1

machines:
  - id: robot
    host: 192.168.1.10
    user: ubuntu
    labels:
      role: edge
  - id: gpu-server
    host: 192.168.1.20
    user: ml
    labels:
      gpu: "true"

dataflow.yml：

nodes:
  - id: camera
    deploy:
      machine: robot
    path: ./camera-driver
    outputs:
      - frames

  - id: inference
    deploy:
      labels:
        gpu: "true"
    path: ./ml-model
    inputs:
      frames: camera/frames
    outputs:
      - predictions

  - id: actuator
    deploy:
      machine: robot
    path: ./actuator-driver
    inputs:
      commands: inference/predictions

2. 多机器人集群

一个中心协调器管理 N 台具有异构硬件的机器人。标签调度会将节点路由到正确的机器，而无需硬编码机器 ID。

cluster.yml：

coordinator:
  addr: 10.0.0.1

machines:
  - id: bot-01
    host: 10.0.0.11
    user: robot
    labels:
      fleet: warehouse
      lidar: "true"

  - id: bot-02
    host: 10.0.0.12
    user: robot
    labels:
      fleet: warehouse
      camera: rgbd

  - id: bot-03
    host: 10.0.0.13
    user: robot
    labels:
      fleet: warehouse
      lidar: "true"
      camera: rgbd

dataflow.yml：

nodes:
  - id: lidar-driver
    deploy:
      labels:
        lidar: "true"
    path: ./lidar-driver
    outputs:
      - scans

  - id: camera-driver
    deploy:
      labels:
        camera: rgbd
    path: ./camera-driver
    outputs:
      - frames

在此配置下，lidar-driver 会运行在 bot-01 或 bot-03 上，而 camera-driver 会运行在 bot-02 或 bot-03 上。

运维手册

初始设置检查清单

  1. SSH 密钥：分发 SSH 密钥，使 CLI 所在机器能够无密码访问所有集群机器（BatchMode=yes）。
  2. Dora 可执行文件：在所有机器上安装 dora 可执行文件（版本相同）。
  3. 网络：确保协调器端口（默认 6013）可从所有机器访问。确保守护进程之间的 Zenoh 端口已开放，以支持跨机器节点通信。
  4. cluster.yml：创建集群配置文件，填写正确的 IP、用户和标签。

日常操作

# Start a dataflow
dora start dataflow.yml --name my-app --attach

# List running dataflows
dora list

# Monitor resource usage
dora top

# View node logs
dora logs my-app <node-id> --follow

# Stop a dataflow
dora stop my-app

# Check cluster health
dora cluster status

Upgrading

  1. 在本地构建或下载新的 dora 可执行文件。
  2. 运行 dora cluster upgrade cluster.yml。
  3. 通过 dora cluster status 确认所有守护进程已重新连接。
  4. 正在运行的数据流会通过自动恢复机制自动重新启动。

故障排查

守护进程无法连接

  • 确认协调器正在运行且可访问：curl http://<addr>:6013/api/health（或查看协调器日志）。
  • 查看守护进程日志：journalctl -u dora-daemon-<id> -f（systemd 方式）或守护进程的 stderr 输出（临时方式）。
  • 确认 --coordinator-addr 和 --coordinator-port 与协调器实际绑定的地址一致。

集群命令执行时 SSH 失败

  • 确认在 CLI 所在机器上执行 ssh -o BatchMode=yes <user>@<host> echo ok 可以成功。
  • 检查 StrictHostKeyChecking=accept-new 是否符合你的环境要求（首次连接会自动接受主机密钥）。
  • 确认 cluster.yml 中的 user 字段与目标机器上有效的 SSH 用户一致。

标签不匹配错误

  • 错误：no daemon matches labels {"gpu": "true"}。
  • 检查守护进程启动时是否使用了正确的 --labels 参数。
  • 运行 dora cluster status 查看已连接的守护进程。标签是在守护进程启动时根据 cluster.yml 设置的，运行时无法更改。

自动恢复未触发

  • 自动恢复仅适用于由协调器管理的数据流（dora start），不适用于 dora run。
  • 查看协调器日志中是否有 auto-recovery: re-spawning 消息。
  • 如果节点立即崩溃，恢复操作会被限流，每个数据流在每个守护进程上最多每 30 秒恢复一次。

部署 YAML 参考

每个节点上的 deploy 部分用于控制放置和分布。所有字段均为可选。

nodes:
  - id: my-node
    deploy:
      machine: edge-01                # Target machine ID from cluster.yml
      labels:                          # Label requirements (superset match)
        gpu: "true"
        arch: arm64
      distribute: local                # local | scp | http
      working_dir: /opt/my-app         # Working directory on the target machine
    path: ./my-node

字段

字段类型默认值描述
machinestring无目标机器 ID。优先级高于标签。
labels映射空所需的守护进程标签。所有键值对都必须匹配。
distributestringlocal可执行文件分发策略：local、scp 或 http。
working_dirpath无目标机器上的工作目录。

解析优先级

  1. machine——如果设置了该字段，节点会分配给具有该机器 ID 的守护进程。
  2. labels——如果设置了该字段（且未设置 machine），节点会分配给标签是所需标签超集的第一个守护进程。
  3. 回退机制——如果两者都未设置，节点会分配给第一个未命名（无 machine-id）的守护进程。

最佳实践

  • 优先使用标签而非机器 ID，以提高灵活性。标签可将数据流与具体机器解耦，便于添加、移除或替换硬件。
  • 生产环境使用 systemd 安装。守护进程服务可在重启后保留，并在失败时通过 Restart=on-failure 自动重启。
  • 在集群中使用协调器持久化（dora coordinator --store redb），使协调器能够在重启后恢复。参见协调器状态持久化。
  • 为节点设置重启策略以实现按节点的弹性恢复。将其与自动恢复结合使用可实现纵深防御。参见重启策略。
  • 结合多种工具进行监控：使用 dora cluster status 查看守护进程健康状态，使用 dora top 查看资源使用情况，使用 dora logs 查看节点输出。
  • 先在本地测试。先用 dora run dataflow.yml 进行开发，再部署到集群。同一份 dataflow YAML 在两种模式下都适用——本地模式下 deploy 字段会被忽略。
  • 使用滚动升级而不是停止整个集群。dora cluster upgrade 会逐台机器处理，以维持可用性。
  • 将 cluster.yml 与数据流定义一起纳入版本控制。
