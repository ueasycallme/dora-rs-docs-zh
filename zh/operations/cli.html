快速开始

# Create a new project
dora new my-robot --kind dataflow --lang rust

# Run locally (no coordinator/daemon needed)
dora run dataflow.yml

# Exit as soon as every node has finished. Without this, a dataflow in
# which any node consumes a `dora/timer/...` input never ends on its
# own: a timer input has no upstream node, so it never closes, and the
# node consuming it is never told its inputs are done.
dora run dataflow.yml --exit-when-nodes-finish

# Or use coordinator/daemon for production
dora up
dora start dataflow.yml --attach
# Ctrl-C to stop
dora down

安装

从 crates.io 安装（推荐）

cargo install dora-cli

从源码安装

cargo install --path binaries/cli --locked

验证

dora --version
dora status

核心概念

数据流

数据流是由多个节点通过有类型的数据通道连接而成的有向图。节点产生输出，供其他节点作为输入消费。该框架负责数据路由、序列化（Apache Arrow）以及生命周期管理。

执行模式

模式命令基础设施使用场景
本地dora run无开发、测试、单机场景
分布式dora up + dora start协调器 + 守护进程生产环境、多机场景

组件角色

CLI  -->  Coordinator  -->  Daemon(s)  -->  Nodes / Operators
              (control plane)  (per machine)    (user code)
  • CLI：用户接口，发送命令、显示日志。
  • 协调器：在多台机器间编排数据流的生命周期。
  • 守护进程：启动节点进程、管理 IPC、收集指标。
  • 节点：产生和消费 Arrow 数据的独立进程。
  • 算子：在共享运行时内运行的进程内代码（相比节点延迟更低）。

数据格式

系统内所有数据均以 Apache Arrow 列式数组的形式流动。这使得同机节点之间可以实现零拷贝共享内存传输，且没有序列化开销。

数据流描述文件

数据流定义在 YAML 文件中。完整的模式如下：

最小示例

nodes:
  - id: sender
    path: sender.py
    outputs:
      - message

  - id: receiver
    path: receiver.py
    inputs:
      message: sender/message

完整模式

# Dataflow-level settings
health_check_interval: 5.0    # health check sweep interval in seconds (default: 5.0)

nodes:
  - id: my-node                 # unique identifier (required)
    name: "My Node"             # human-readable name (optional)
    description: "..."          # description (optional)

    # --- Source (pick one) ---
    path: ./target/debug/my-node          # local executable
    # path: https://example.com/node.zip  # download from URL
    # git: https://github.com/org/repo.git  # build from git
    #   branch: main            # git branch (mutually exclusive with tag/rev)
    #   tag: v1.0               # git tag
    #   rev: abc123             # git commit hash

    # --- Build ---
    build: cargo build -p my-node   # shell command to build (optional)

    # --- Inputs ---
    inputs:
      # Short form: source_node/output_id
      tick: dora/timer/millis/100
      data: other-node/output

      # Long form with options
      sensor_data:
        source: sensor/frames
        queue_size: 10            # input buffer size (default: 10)
        queue_policy: drop_oldest # or "backpressure" (buffers up to 10x queue_size)
        input_timeout: 5.0        # circuit breaker timeout in seconds

    # --- Outputs ---
    outputs:
      - processed
      - status

    # --- Environment ---
    env:
      MY_VAR: "value"
      FROM_ENV:
        __dora_env: HOST_VAR     # read from host environment
    args: "--verbose"             # command-line arguments

    # --- Fault tolerance ---
    restart_policy: on-failure    # never (default) | on-failure | always
    max_restarts: 5               # 0 = unlimited
    restart_delay: 1.0            # initial backoff in seconds
    max_restart_delay: 30.0       # backoff cap in seconds
    restart_window: 300.0         # reset counter after N seconds
    health_check_timeout: 30.0    # kill if no activity for N seconds

    # --- Logging ---
    min_log_level: info           # source-level filter (daemon-side)
    send_stdout_as: raw_output    # route raw stdout as data output
    send_logs_as: log_entries     # route structured logs as data output
    max_log_size: "50MB"          # rotate log files at this size
    max_rotated_files: 5          # number of rotated files to keep (0-100)

    # --- Deployment ---
    deploy:
      machine: A                  # target machine/daemon ID

# Debug settings
debug:
  enable_debug_inspection: true   # required for topic echo/hz/info

内置定时器节点

定时器是以固定间隔发出 tick 的虚拟节点：

inputs:
  tick: dora/timer/millis/100   # every 100ms
  slow: dora/timer/millis/1000  # every 1s
  fast: dora/timer/hz/30        # 30 Hz (~33ms)

算子节点

算子在共享运行时内以进程内方式运行（无需独立进程）：

nodes:
  # Single operator (shorthand)
  - id: detector
    operator:
      python: detect.py
      build: pip install -r requirements.txt
      inputs:
        image: camera/frames
      outputs:
        - bbox

  # List form with an explicit operator id (a runtime node holds exactly
  # one operator; outputs are referenced as runtime-node/preprocessor/<output>)
  - id: runtime-node
    operators:
      - id: preprocessor
        shared-library: ../../target/debug/libpreprocess
        inputs:
          raw: sensor/data
        outputs:
          - processed

分布式部署

使用 deploy 将节点分配到特定机器：

nodes:
  - id: camera-driver
    deploy:
      machine: robot-arm
    path: ./target/debug/camera
    outputs:
      - frames

  - id: ml-inference
    deploy:
      machine: gpu-server
    path: ./target/debug/inference
    inputs:
      frames: camera-driver/frames
    outputs:
      - predictions

当节点位于不同机器上时，通信会自动从共享内存切换到 Zenoh pub/sub。

命令参考

生命周期命令

dora run

独立地在本地运行数据流：通过守护进程库以进程内方式启动节点，不绑定任何协调器端口。最适合开发和测试使用。

由于 dora run 不绑定协调器端口：

  • 即使 dora up 已在运行，也可以调用它（不存在端口争用）。
  • 可以并行执行多个 dora run 调用。
  • CLI 监控命令（dora list、dora stop、dora logs、dora top 等）不会连接到 dora run 的执行实例。如果需要使用这些工具进行连接，请改用 dora up + dora start。
dora run <PATH> [OPTIONS]
参数/标志默认值描述
<PATH>必需数据流描述文件 YAML 的路径
--stop-after <DURATION>经过指定时长后自动停止（例如 30s、5m）
--uvfalse使用 uv 进行 Python 节点管理
--debugfalse启用调试话题（等效于 enable_debug_inspection: true）
--allow-shell-nodesfalse启用基于 shell 的节点执行
--exit-when-nodes-finish[=BOOL]描述文件当所有节点都结束后退出，将 dora/timer/... 类输入视为时钟而非工作任务。会覆盖 YAML 中的 exit_when_nodes_finish:；省略此项则由 YAML 决定
--log-level <LEVEL>stdout最低显示级别：error|warn|info|debug|trace|stdout
--log-format <FORMAT>pretty输出格式：pretty|json|compact；json 会输出 JSON Lines 格式（每条日志消息一个对象）
--log-filter <FILTER>按节点覆盖级别："node1=debug,node2=warn"
--lockedfalse使用构建锁文件中固定的 git 源提交
--write-lockfilefalse在运行前构建过程中将解析出的 git 源提交写入锁文件
--lockfile <PATH><dataflow-stem>.dora-lock.yaml覆盖锁文件路径

示例：

# Basic run
dora run dataflow.yml

# Stop after 10 seconds, only show warnings
dora run dataflow.yml --stop-after 10s --log-level warn

# Python dataflow with uv
dora run dataflow.yml --uv

# Debug one node, silence others
dora run dataflow.yml --log-level warn --log-filter "sensor=debug"

# JSON output for CI pipelines
dora run dataflow.yml --log-format json --stop-after 30s 2>test.json

dora up

以本地模式启动协调器和守护进程。

dora up
dora up --recreate-store

将 dora coordinator 和 dora daemon 作为后台进程启动，等待两者都准备就绪后再返回。具有幂等性：若已在运行，则不做任何操作。

标志描述
--auth为协调器启用 token 认证
--recreate-store归档 ~/.dora/coordinator.redb 并以全新的持久化存储启动

如果协调器无法启动，dora up 会直接报告其启动错误。若升级后报告了不兼容的 redb 模式，请使用 --recreate-store 重新运行。旧的存储会被保留在新存储旁边，命名为 coordinator.redb.backup（或带编号的变体）。

所启动协调器的 stderr 会被捕获到 ~/.dora/coordinator-stderr.log（每次 dora up 都会截断该文件），以便启动后发生的错误仍可查阅。--recreate-store 仅作用于本地默认存储：当 DORA_COORDINATOR_ADDR 指向非回环地址时会被拒绝；当已有协调器在运行时会被跳过（并给出提示）；当有进程监听协调器端口但连接失败（例如认证 token 不匹配）时会中止——因此正在运行的协调器的存储永远不会被在其运行期间归档。

dora down（别名：dora destroy）

关闭协调器和守护进程。会先停止所有正在运行的数据流。

dora down [OPTIONS]
标志默认值描述
--forcefalse即使协调器上有正在运行的数据流，也强制关闭，先立即终止这些数据流
--coordinator-addr <IP>127.0.0.1协调器地址
--coordinator-port <PORT>6013协调器端口

这是机器级别的操作，而非项目级别的。dora down 没有“你的”数据流或“你的”工作副本的概念：它会连接到占用该端口的任何协调器，并将其连同其守护进程以及其上运行的所有数据流一起销毁。同一台机器上的两个工作副本默认共享 127.0.0.1:6013，因此在其中一个副本上执行 dora down 会悄无声息地终止另一个副本的工作——在受害一方看来，这与协调器崩溃没有区别。

自 #2924 起，当目标机器上有正在运行的数据流时，该命令会拒绝执行并列出这些数据流。--force 则会继续执行，先停止每个数据流。

停机操作不会留下残留节点。每个守护进程都会等待停止宽限期结束，并在退出前杀掉仍在运行的进程，因此忽略协作式停止的节点会被终止而不是被遗弃（#2980）。因此，一个卡死的节点会使 dora down 耗时长达整个宽限期；行为良好的节点则会立即退出，不会产生任何耗时。

要并行运行多个实例，需为每个实例指定独立的端口——这就是隔离机制，所有生命周期命令（up、down、start、stop、list、logs）都遵循这一机制：

DORA_COORDINATOR_PORT=6113 dora up
DORA_COORDINATOR_PORT=6113 dora start flow.yml
DORA_COORDINATOR_PORT=6113 dora down     # touches only this instance

dora build

运行数据流描述文件中定义的构建命令。

dora build <PATH> [OPTIONS]
标志默认值描述
<PATH>必需数据流描述文件路径
--uvfalsePython 构建使用 uv
--localfalse强制本地构建（跳过协调器）
--strict-typesfalse将类型警告视为错误（返回非零退出码）

类型检查：展开模块后，build 会运行与 validate 相同的类型检查。默认只打印警告；使用 --strict-types（或在 YAML 中设置 strict_types: true）可在类型不匹配时让构建失败。数据流旁的 types/ 目录中定义的用户自定义类型会自动加载。

构建策略：如果节点包含 deploy 部分且协调器可达，构建会被分发到目标机器；否则在本地运行构建。

Git 源：带有 git: 字段的节点会在构建前被克隆/更新。构建命令从 Git 仓库根目录运行。

托管的 Python 环境（--uv）：对于 Python 节点（带 build: 代码块的 .py 自定义节点，以及带有 Python 算子的运行时节点），--uv 现在会为每个节点在 <working-dir>/.dora/python-envs/<node-id>/ 创建一个专属的 uv 虚拟环境。构建命令会在该虚拟环境中运行，并设置 VIRTUAL_ENV，同时将该环境的 bin/（Windows 上为 Scripts/）前置到 PATH 中。dora start 和 dora run 在启动时会自动复用相同的解释器，因此 Python 节点看到的正是构建时安装的依赖——不再存在构建与运行时之间的漂移，也不会在节点间产生污染。没有 build: 代码块的自定义 Python 节点仍沿用调用方环境中已有的 uv 环境。该环境在后续构建中会被复用（而不会重新创建）。

dora start

在运行中的协调器上启动一个数据流。

如果一个带有 deploy 部分的数据流上次是在本地构建的（通过 dora build --local，或在没有可达协调器的情况下执行 dora build），它会被拒绝并给出可操作的错误提示：运行这些部署目标的远程守护进程无法访问本地构建产物。请在执行 dora start 之前，针对运行中的协调器重新运行 dora build（#1956）。

dora start <PATH> [OPTIONS]
标志默认值描述
<PATH>必需数据流描述文件路径
--name <NAME>, -n为数据流指定一个名称
--attachauto附加到日志流并等待完成
--detachauto启动后立即返回
--debugfalse启用调试话题（等效于 enable_debug_inspection: true）
--hot-reloadfalse监视 Python 文件变化并自动重新加载
--uvfalsePython 节点使用 uv
--exit-when-nodes-finish[=BOOL]描述文件等所有节点都完成后才结束，将 dora/timer/... 输入视为时钟而非工作任务。该选项会覆盖 YAML 中的 exit_when_nodes_finish:；省略该选项则由 YAML 决定。
--coordinator-addr <IP>127.0.0.1协调器地址
--coordinator-port <PORT>6013协调器端口

如果 --attach 和 --detach 都未指定：在 TTY 中运行时会附加，否则会分离。

附加模式：流式输出日志，优雅处理 Ctrl-C（第一次 = 停止，第二次 = 强制终止）。

热重载：监视 Python 算子源文件。发生变化时，向协调器发送重新加载请求，并由协调器传播到守护进程。

已知限制——通过原子重命名方式保存的编辑器（vim、JetBrains、部分 IDE）：监视器只在 notify-rs 发出的 Modify(Data) 事件时触发，但 vim 默认的保存流程是写入一个临时文件再重命名覆盖原文件，这会表现为 Remove(File) 事件，从而导致重新加载错过此次更改。详见 #530 以及上游 notify-rs 的讨论 notify-rs/notify#247。

在 #530 的修复落地之前的临时解决方法：将编辑器配置为原地写入，而不是原子重命名。

  • vim / neovim：在 .vimrc 中添加 :set backupcopy=yes，或按会话临时设置。这会让 vim 复制文件并原地覆盖（而不是先写临时文件再重命名）。
  • JetBrains IDE（PyCharm、IntelliJ）：Settings → Appearance & Behavior → System Settings，取消勾选“Use 'safe write'（save changes to a temporary file first）”。
  • VS Code：默认即为原地写入，无需任何变通方案。

dora stop

停止一个正在运行的数据流。

dora stop [UUID_OR_NAME] [OPTIONS]
标志默认值描述
[UUID_OR_NAME]interactive数据流 UUID 或名称
--name <NAME>, -n可选的名称指定方式
--grace-duration <DURATION>优雅关闭超时时间
--force, -ffalse立即终止
--coordinator-addr <IP>127.0.0.1协调器地址
--coordinator-port <PORT>6013协调器端口

如果未提供标识符且在 TTY 中运行，会呈现一个交互式选择器。

停止流程：发送 Event::Stop -> 等待宽限期 -> SIGTERM -> 强制终止。

dora restart

重启一个正在运行的数据流（先停止，再用已保存的描述文件重新启动）。无需提供 YAML 路径——协调器保留了原始的描述文件。

dora restart [UUID] [OPTIONS]
标志默认值描述
[UUID]数据流 UUID
--name <NAME>, -n按名称而非 UUID 重启
--grace-duration <DURATION>停止阶段的优雅关闭超时时间
--force, -ffalse重启前强制终止
--coordinator-addr <IP>127.0.0.1协调器地址
--coordinator-port <PORT>6013协调器端口

示例：

# Restart by name
dora restart --name my-app

# Restart by UUID with forced stop
dora restart a1b2c3d4-... --force

dora record

将数据流消息记录到 .drec 文件中以便离线回放。完整流程参见调试指南。

dora record <DATAFLOW_YAML> [OPTIONS]
标志默认值描述
<DATAFLOW_YAML>必需数据流描述文件的路径
-o, --output <PATH>recording_{timestamp}.drec输出文件路径
--topics <TOPICS>all以逗号分隔的 node/output 话题，用于录制
--proxyfalse通过 WebSocket 流式传输，而不是在目标上录制
--output-yaml <PATH>写入修改后的 YAML 而不运行（dry run）
--queue-size <N>100注入的录制节点每个话题的队列深度

默认模式会向数据流中注入一个录制节点。--proxy 模式需要一个正在运行的数据流，并设置 enable_debug_inspection: true。

录制完整性。注入的录制节点会写入磁盘，因此生产者的突发流量或写入停滞都可能使其跟不上节奏，它来不及接收的消息会在写入器看到之前就被丢弃。--queue-size 决定每个被录制话题能获得多少缓冲余量；这个深度还决定了该节点 zenoh 入口通道的大小，而这正是零拷贝负载（>=4 KB）真正会溢出的地方。调大它可以撑过更长时间的停滞，代价是缓冲负载占用的内存——每个话题的峰值常驻内存大约是 2 x queue_size x payload size（每个输入的调度器队列和共享入口通道各自都可能占满整个深度），对视频帧来说这是一笔不小的开销。对于达到或超过零拷贝阈值的负载，一条被缓冲的消息还会固定（pin）住其共享内存区域：一旦停滞的录制器占用的区域超过生产者内存池（DORA_NODE_SHM_POOL_SIZE，默认 8 MiB）所能腾出的空间，该生产者就会为其所有消费者回退到堆内存拷贝。

运行结束时会按话题报告被丢弃的消息，摘要会标注 INCOMPLETE，这样一段较短的 .drec 就不会被误认为是完整录制。长时间录制在第一次丢弃消息时也会在 stderr 上发出警告。一次干净的运行会报告“未检测到消息丢失”而不是“complete（完整）”：生产者以 CongestionControl::Drop 方式发布，因此在 zenoh 出口被丢弃的消息永远不会到达录制器的计数器，而零丢弃意味着在录制器可观察到的所有路径上都没有发生丢失。

录制节点特意不在其输入上设置 queue_policy: backpressure。该策略会把生产者的全部输出都固定在守护进程路径上，对每个消费者都是如此，这样录制一个数据流就会把其流量移出零拷贝路径，从而改变被测量的对象——况且这个策略本身也不是无损的（它会在 10x queue_size 时丢弃消息）。录制器绝不能扰动它所观测的系统。

dora clean

从协调器的状态中移除已完全结束的数据流。正在运行的数据流不受影响。对于多守护进程的数据流，如果部分守护进程已结束而另一些尚未结束，也会被跳过——清理操作只处理没有任何守护进程仍在运行的数据流。

dora clean [OPTIONS]
标志默认值描述
--format <FMT>, -ftable输出格式：table|json。JSON 输出使用 JSON Lines（每行一个对象）；每个失败项也会在 stderr 上以一行 JSON 对象的形式输出，随后附带一段纯文本错误摘要（退出码为非零）
--quiet, -qfalse仅输出已清理的 UUID
--coordinator-addr <IP>127.0.0.1协调器地址
--coordinator-port <PORT>6013协调器端口

清理内容：来自 dataflow_results 的已完全完成数据流的记录及其已归档的描述文件，以及任何仅存在于持久化存储中（redb 中落盘）而不在内存中的 Succeeded/Failed 记录——这通常是协调器重启之前的历史记录行，因为恢复循环有意不会将已完成的数据流重新加载到内存中。协调器会先从持久化存储中删除每条已清理的条目，然后才将其从内存状态中移除——因此一个数据流只有在两侧都真正被清理后才会出现在该命令的输出中。持久化存储的删除会级联到属于该已清理数据流的每一行 dora param，以避免状态文件无限增长。缓存的构建结果（finished_builds）会被有意保留——清除它们会破坏并发的 dora build 调用。

部分失败时的行为：如果持久化存储删除对一个或多个数据流失败，这些数据流会保留其内存中的记录，以便之后的 dora clean 可以重试。CLI 会针对每个失败在 stderr 上打印一行 warning:，并以非零状态退出，以区分“部分故障”和“没有符合清理条件的对象”这两种情况。如果持久化存储枚举本身失败（例如 redb 文件不可读），协调器会以错误回复直接使该请求彻底失败，并保持所有状态不变——待存储恢复正常后，下一次清理会重试。

会丢失的内容：清理之后，dora logs <uuid> 对已清理的数据流将不再有效，持久化记录也已消失（因此针对该已清理 UUID 的 dora param 也会失败）。在运行 dora clean 之前，请先保存任何以后可能需要参考的内容。

何时使用：当 dora list 中堆积了大量来自以往运行的已完成/失败数据流，或长期运行的协调器的 redb 状态文件已变得过大时。比 dora down + dora up 破坏性更小——协调器保持运行，守护进程也保持连接。

dora validate

校验一个 dataflow YAML 文件并检查类型注解。

dora validate <PATH> [OPTIONS]
标志默认值描述
<PATH>必需数据流描述文件路径

  7. 元数据模式：会校验 output_metadata 键和 pattern 简写形式
  8. 模式（Schema）兼容性：结构体类型会在字段级别进行检查（缺失/错误的字段）

位于数据流旁的 types/ 目录中的用户自定义类型会被自动加载。

# Strict mode for CI (exit 1 on warnings)

协议分层

层传输方式格式用途
CLI <-> 协调器WebSocketJSON（ControlRequest/Reply）命令、日志流式传输
协调器 <-> 守护进程WebSocketJSON（DaemonCoordinatorEvent）节点生命周期、指标

协调器内部原理

协调器是一个事件驱动的异步服务器：

Event Sources:
  - CLI WebSocket connections (ControlRequest)
  - Daemon WebSocket connections (DaemonEvent)
  - Heartbeat timer (3s interval)
  - External events (for embedding)

Event Loop:
  merge_all(cli_events, daemon_events, heartbeat, external)
    -> handle_event()
    -> update state
    -> persist to store (if redb)
    -> send replies

关键类型：

RunningBuild    { build_id, errors, log_subscribers, pending_results, ... }
DaemonConnection { sender, pending_replies, last_heartbeat }

    fn get_dataflow(&self, uuid: &Uuid) -> Result<Option<DataflowRecord>>;

存储后端：

  • memory（默认）：存于内存中，重启后丢失。
  • redb：持久化到磁盘（~/.dora/coordinator.redb），可在崩溃后恢复，需要 redb-backend 特性。
dora coordinator --store redb
dora coordinator --store redb:/custom/path.redb

守护进程内部原理

守护进程负责管理单台机器上的节点进程：

Per Node:
  1. Build (if build command specified)
  2. Spawn process with DORA_NODE_CONFIG env var
  3. Node registers via TCP/shmem handshake
  4. Route inputs/outputs between nodes
  5. Collect metrics (CPU, memory, I/O)
  6. Handle restart policy on exit
  7. Forward logs to coordinator

Communication:
  - Shared memory for messages > 4KB (zero-copy)
  - TCP for control messages and small data
  - flume channels for internal event routing

消息类型

所有组件间消息都定义在 libraries/message/ 中：

#![allow(unused)]
fn main() {
// Node identification
struct NodeId(String);      // [a-zA-Z0-9_.-], no leading `.`, not `dora`
struct DataId(String);      // same validation
type DataflowId = uuid::Uuid;

// Data metadata
struct Metadata {
    timestamp: uhlc::Timestamp,    // hybrid logical clock
    type_info: ArrowTypeInfo,      // Arrow schema
    parameters: MetadataParameters, // custom key-value pairs
}

// Node events (daemon -> node)
enum NodeEvent {
    Stop,
    Reload { operator_id },
    Input { id, metadata, data },
    InputClosed { id },
    InputRecovered { id },
    NodeRestarted { id },
    AllInputsClosed,
}
}

时间戳

Dora 使用统一混合逻辑时钟（UHLC）来处理分布式因果关系。每条消息都携带一个 uhlc::Timestamp，可在没有同步时钟的情况下跨机器保持因果顺序。

零拷贝共享内存

对于较大的消息（> 4KB），守护进程会使用共享内存区域：

  1. 发送方节点向守护进程请求一个共享内存槽位
  2. 守护进程分配一个区域并返回其 ID
  3. 发送方将 Arrow 数据直接写入共享内存
  4. 守护进程将该区域 ID 通知给接收方节点
  5. 接收方直接从共享内存读取（零拷贝）
  6. 接收方处理完成后发送一个释放令牌（drop token）

这使大负载场景下的延迟比 ROS2 低 10 到 17 倍。

编写节点

Rust 节点

use dora_node_api::{DoraNode, Event, IntoArrow};
use dora_core::config::DataId;

fn main() -> eyre::Result<()> {
    let (mut node, mut events) = DoraNode::init_from_env()?;

    let output = DataId::from("result".to_owned());

    while let Some(event) = events.recv() {
        match event {
            Event::Input { id, metadata, data } => {
                // Process input data (Arrow array)
                let result: u64 = 42;
                node.send_output(
                    output.clone(),
                    metadata.parameters,
                    result.into_arrow(),
                )?;
            }
            Event::Stop(_) => break,
            Event::InputClosed { id } => {
                eprintln!("input {id} closed");
            }
            Event::InputRecovered { id } => {
                eprintln!("input {id} recovered");
            }
            _ => {}
        }
    }
    Ok(())
}

编写算子

算子在共享运行时内以进程内方式运行，避免了启动新进程的开销。

Rust 算子

#![allow(unused)]
fn main() {
use dora_operator_api::{register_operator, DoraOperator, DoraOutputSender, DoraStatus, Event};

#[register_operator]
#[derive(Default)]
pub struct MyOperator {
    counter: u32,
}

impl DoraOperator for MyOperator {
    fn on_event(
        &mut self,
        event: &Event,
        output_sender: &mut DoraOutputSender,
    ) -> Result<DoraStatus, String> {
        match event {
            Event::Input { id, data } => {
                self.counter += 1;
                output_sender.send(
                    "count".to_string(),
                    arrow::array::UInt32Array::from(vec![self.counter]),
                )?;
                Ok(DoraStatus::Continue)
            }
            Event::Stop => Ok(DoraStatus::Stop),
            _ => Ok(DoraStatus::Continue),
        }
    }
}
}

协调器持久化

在生产环境中，请使用 redb 存储后端，以便协调器在重启后仍能保留状态：

dora coordinator --store redb

状态会持久化到 ~/.dora/coordinator.redb。重启后，陈旧的数据流会被标记为失败，协调器会恢复正常运行。

对于受管理的集群部署（cluster.yml、基于 SSH 的生命周期管理、标签调度、systemd 服务、滚动升级），请参阅分布式部署指南。

常见问题

“无法连接到 dora-coordinator”

  • 先运行 dora up，或检查 DORA_COORDINATOR_ADDR / DORA_COORDINATOR_PORT
  • 用 dora status 验证

“未启用 enable_debug_inspection”

  • 使用 --debug 参数：dora start dataflow.yml --debug 或 dora run dataflow.yml --debug
  • 或者添加到你的 dataflow YAML 中：
    debug:
  enable_debug_inspection: true
  • topic echo、topic hz、topic info 需要此项

“dora top 需要交互式终端”

  • 这些 TUI 命令需要真实终端（不能是管道输出）
  • topic hz 同理

节点未收到输入

  • 检查输出名称是否匹配：source_node/output_id
  • 确认源节点的 outputs: 数组中列出了该输出
  • 用 dora topic list 检查可用话题

日志未出现

  • 检查 --log-level 设置（默认 stdout 会显示所有内容）
  • 检查 YAML 中的 min_log_level（在源头过滤）
  • 分布式场景下：验证协调器 / 守护进程的连通性

使用 git 来源构建失败

  • 确认 git: URL 可访问
  • 检查 branch、tag 或 rev 是否存在
  • 构建命令是从 git 仓库根目录运行的，而不是数据流目录

调试工作流

# 1. Full environment diagnosis
dora doctor --dataflow dataflow.yml

# 2. Start with verbose logging and debug topics
dora run dataflow.yml --log-level trace --debug

# 3. Inspect a specific node
dora node info -d my-dataflow problem-node

# 4. Monitor specific node logs
dora logs my-dataflow --node problem-node --follow --level debug

# 5. Check resource usage
dora top

# 6. Inspect topic data
dora topic echo -d my-dataflow problem-node/output

# 7. Publish test data to a topic
dora topic pub -d my-dataflow problem-node/input '[1, 2, 3]'

# 8. Measure frequencies
dora topic hz -d my-dataflow --window 5

# 9. View/modify runtime parameters
dora param list -d my-dataflow problem-node
dora param set -d my-dataflow problem-node threshold 42

# 10. Restart a misbehaving node without stopping the dataflow
dora node restart -d my-dataflow problem-node

# 11. View coordinator traces (no external infra needed)
dora trace list
dora trace view <trace-id-prefix>

# 12. Visualize dataflow graph
dora graph dataflow.yml --open
