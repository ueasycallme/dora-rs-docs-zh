Dora 用户指南

ROS2 桥接

dora 通过显式选择的传输方式与 ROS2 生态（话题、服务（Service）、动作（Action）、参数）通信。DDS 使用纯 Rust 的 ros2-client + rustdds 技术栈，并仍是默认选项。原生 Zenoh 直接使用 rmw_zenoh_cpp 线路协议。这两条路径都不链接 rcl/rclcpp；数据以 Apache Arrow 的 StructArray 形式传递，在边界处与 ROS2 CDR 相互转换。

传输选择

省略 transport 将保留 DDS 行为。原生 Zenoh 必须显式选择一个身份配置文件：

ros2:
  transport:
    kind: zenoh
    compatibility: humble # legacy TypeHashNotSupported identity
    config_uri: /etc/zenoh/session.json5 # optional
  topic: /chatter
  message_type: std_msgs/String
  direction: subscribe

对 Humble 版本的 rmw_zenoh_cpp 分支使用 compatibility: humble，对发布 REP-2016 类型哈希的发行版使用 compatibility: rep2016。该配置文件从不自动检测：故意选错会得到一个空图，而不是去猜测一个不兼容的线路身份。

线路契约遵循上游的 rmw_zenoh 设计，包括 CDR 载荷、附件、键以及存活性令牌（liveliness token）。现代配置文件从 REP-2016 类型描述哈希中派生身份。

在启动数据流之前启动该发行版的 rmw_zenohd。Zenoh 配置的优先级依次为：显式的 config_uri，然后是 ZENOH_SESSION_CONFIG_URI，最后是内嵌的默认值。显式设置为空的 URI 是无效的。ROS_DOMAIN_ID 默认为 0；图（graph）和数据键按域（domain）划分范围，命名空间仍是 ROS 完全限定端点名称的一部分。

支持的中立 QoS 包括 reliability（可靠性）、volatile/transient-local durability（持久性）、keep-last/keep-all history（历史记录）以及 automatic/manual liveliness（活跃性）。transient-local 的回放受所配置历史记录的限制。zenoh-bridge-ros2dds 进程不能替代此模式：它桥接的是 DDS 图，而原生模式必须直接匹配 rmw_zenoh_cpp 的数据键、活跃性令牌、附件以及类型标识。

使用该桥接有两种方式，本指南将予以介绍：

  1. YAML / 动态桥接——在节点上添加 ros2: 键，框架便会启动一个桥接二进制程序；你的节点代码保持与 ROS2 无关，只交换纯 Arrow 数据。与语言无关，无需编写代码。这是本指南的主要内容。
  2. 原生代码 API——在节点代码中通过类型化的、按语言区分的 API 直接调用 ROS2：Python（dora.Ros2Context）接口，以及代码生成产生的 Rust / C++ 接口。当你想从节点以命令式方式驱动 ROS2 时，可使用这些接口。参见下文的原生代码 API。

架构

当 Dora 描述文件解析器在节点上遇到 ros2: 键时，会将其转换为指向 dora-ros2-bridge-node 二进制程序的 Custom 节点。桥接配置会被序列化为 JSON，存入 DORA_ROS2_BRIDGE_CONFIG 环境变量。

User Node <--(Arrow/SharedMem)--> Bridge Binary <--(CDR over DDS or Zenoh)--> ROS2

该桥接二进制程序会：

  1. 读取 AMENT_PREFIX_PATH 以定位已安装的 ROS2 消息包
  2. 在启动时解析消息/服务/动作定义
  3. 创建一个中立的桥接节点，以及特定后端的发布者、订阅者、客户端或服务端
  4. 将接收到的 ROS2 CDR 消息转换为 Arrow StructArray（订阅/响应/反馈）
  5. 将接收到的 Arrow StructArray 转换为 ROS2 CDR 消息（发布/请求/目标）

你的用户节点永远不会链接 ROS2——所有 ROS2 通信都隔离在桥接二进制程序内。

原生 Zenoh 故障排查

  • 图为空：确认 rmw_zenohd 正在运行，两个进程使用相同的 ROS_DOMAIN_ID，并且 Dora 选择了与对端分布匹配的 profile。
  • 缺少类型哈希：rep2016 需要 AMENT_PREFIX_PATH 中该软件包已安装的 JSON 类型描述。Humble 版本则会改为公布旧版的 TypeHashNotSupported 标识。
  • 路由不可用：检查所配置的端点以及配置文件的权限。显式指定的 config_uri 会覆盖 ZENOH_SESSION_CONFIG_URI。
  • 端点可见但调用挂起：确认 ROS 对端确实使用了 rmw_zenoh_cpp；DDS RMW 或 zenoh-bridge-ros2dds 图是不同的通信线路约定。设置 DORA_ROS2_ZENOH_TRACE=1 可打印原生活跃性活动。

前置条件

  • 已加载 ROS2 环境：必须设置 AMENT_PREFIX_PATH，并指向包含所需消息包的工作空间
  • 已安装消息包：例如 turtlesim、geometry_msgs、example_interfaces
  • 对于服务客户端：必须有正在运行的 ROS2 服务服务端（或使用配套的服务端数据流）
  • 对于动作客户端：在启动数据流之前必须有正在运行的 ROS2 动作服务端（没有 wait_for_action_server 机制）
  • 对于动作服务端：需要有 ROS2 动作客户端向桥接发送目标（例如使用 ros2 action send_goal）

为你的 ROS 发行版构建

已发布的桥接构建针对 Humble。在其他发行版上，须先用匹配的 feature 构建后再运行数据流，否则桥接会输出日志 ROS_DISTRO='jazzy' but ros2-client was built for 'humble'。

ros2-humble（默认）、ros2-iron、ros2-jazzy 和 ros2-kilted 这几个 feature 对整个构建来说是单选项，而不是可叠加的集合。ros2-client 会按它所见到的最新发行版 feature 进行编译，所以 ros2-jazzy 会用 Jazzy 的 16 字节 Gid 替换 Humble 的 24 字节版本，而不是在 Humble 之外再加上 Jazzy 支持，且没有任何 dora feature 能把它切换回去。由于 Cargo 会在整个构建中统一 ros2-client 的 feature，在任何其他 crate 中启用更新的发行版也会一并切换桥接——即便是那个以默认 feature 依赖 ros2-client 的 crate 也不例外，因为它自身的默认值就是 jazzy。Humble 只是工作区固定的下限，因此无法强制恰好使用 Humble。构建期不会有任何警告；请检查启动时的 ROS_DISTRO 日志——ros2-client 在不匹配时会记录为 error，在 ROS_DISTRO 未设置时会记录为 warning。

  • YAML 桥接：dora-ros2-bridge-node 并未随 CLI 一起分发，因此需要为你的发行版单独安装它，并保留在 PATH 中（解析器会按名称启动它）：

    cargo install --git https://github.com/dora-rs/dora dora-ros2-bridge-node --features ros2-jazzy

  • 进程内 Python（from dora import Ros2Context）：dora-rs wheel 链接了该桥接，因此需要用 maturin 重新构建它：

    maturin build -m apis/python/node/Cargo.toml --features ros2-jazzy

  • C++ 节点：dora-node-api-cxx 本身没有任何 ros2-* feature，会得到 Humble 默认值，因此若要面向其他发行版，需要直接启用 dora-ros2-bridge/ros2-jazzy。

话题桥接

单一话题（订阅）

订阅一个 ROS2 话题，并把消息作为 Arrow 数据转发给下游的 Dora 节点。

nodes:
  - id: pose_bridge
    ros2:
      topic: /turtle1/pose
      message_type: turtlesim/Pose
      direction: subscribe       # default, can be omitted
    outputs:
      - pose

该桥接在 /turtle1/pose 上创建一个 ROS2 订阅，把每条收到的 turtlesim/Pose 消息反序列化为 Arrow 的 StructArray，然后通过 pose 输出发送出去。

单一话题（发布）

从 Dora 节点接收 Arrow 数据，并发布到一个 ROS2 话题。

nodes:
  - id: cmd_bridge
    ros2:
      topic: /turtle1/cmd_vel
      message_type: geometry_msgs/Twist
      direction: publish
    inputs:
      cmd_vel: planner/cmd_vel

该桥接在 cmd_vel 输入上接收 Arrow 数据，将其序列化为 geometry_msgs/Twist CDR 格式，并发布到 /turtle1/cmd_vel。

多话题

在单个 ROS2 节点上下文中桥接多个话题，可混合订阅和发布方向。

nodes:
  - id: turtle_bridge
    ros2:
      topics:
        - topic: /turtle1/pose
          message_type: turtlesim/Pose
          direction: subscribe
          output: pose
        - topic: /turtle1/cmd_vel
          message_type: geometry_msgs/Twist
          direction: publish
          input: velocity
      qos:
        reliable: true
        keep_last: 10
    inputs:
      velocity: planner/cmd_vel
    outputs:
      - pose

多话题模式下，每个桥接节点最多支持 64 个话题。

输入/输出 ID 映射

话题名称会通过去掉开头的 / 并把剩余的 / 替换为 _，映射为一个派生出来的 Dora ID：

ROS2 话题派生出的 Dora ID
/turtle1/poseturtle1_pose
/camera/image_rawcamera_image_raw

在多话题模式下，可以用明确的 output（用于订阅）或 input（用于发布）字段覆盖这个映射；若未覆盖，派生出的 id 必须是该节点已声明的端口之一，否则该数据流会被拒绝。

在单一话题模式下不存在 output/input 字段，因此会直接使用该节点已声明的端口：topic: /turtle1/pose 配合 outputs: [pose] 会绑定到 pose。当节点声明了多个端口时，这个选择就会产生歧义，该数据流会被拒绝——除非其中有一个端口正好是派生出的 id，这时它会被优先采用（这样桥接节点仍可以额外声明一个 send_stdout_as 输出）。当你需要多个端口并使用自定义名称时，请使用带明确映射的多话题模式。

服务（Service）桥接

服务（Service）客户端

从 Dora 向外部 ROS2 服务发送请求并接收响应。

nodes:
  - id: add_client
    ros2:
      service: /add_two_ints
      service_type: example_interfaces/AddTwoInts
      role: client
    inputs:
      request: requester/data
    outputs:
      - response

该桥接会等待服务变为可用状态（最多重试 10 次，每次间隔 2 秒），然后对每个收到的 Arrow 输入执行：

  1. 将 Arrow 数据序列化为 AddTwoInts_Request CDR 消息
  2. 将请求发送到 ROS2 服务
  3. 等待响应（超时时间 30 秒）
  4. 把响应反序列化为 Arrow 数据，并通过 response 输出发送出去

服务（Service）服务端

将一个 Dora 处理节点暴露为 ROS2 服务，供外部 ROS2 客户端调用。

nodes:
  - id: add_server
    ros2:
      service: /dora_add_two_ints
      service_type: example_interfaces/AddTwoInts
      role: server
    inputs:
      response: handler/result
    outputs:
      - request

  - id: handler
    path: path/to/handler-node
    inputs:
      request: add_server/request
    outputs:
      - result

该桥接接收 ROS2 服务请求，为每个请求分配一个唯一的 request_id（UUID v7），将请求数据作为 Arrow 通过 request 输出转发出去，并在元数据中携带 request_id，然后等待处理节点在 response 输入上以相同的 request_id 发回响应。随后该响应会被返回给正确的 ROS2 客户端。

可参考 examples/ros2-bridge/yaml-bridge-service/ 中的可运行示例。

请求 ID 关联

每个收到的 ROS2 请求都会被赋予一个 request_id 元数据参数。处理节点在发送响应时必须在元数据中带上相同的 request_id。最简单的做法是透传 metadata.parameters：

#![allow(unused)]
fn main() {
Event::Input { id, metadata, data } => {
    // metadata.parameters contains request_id
    let result = compute(data);
    node.send_service_response("response".into(), metadata.parameters, result)?;
}
}

响应可以以任意顺序到达——桥接是按 request_id 而不是按到达顺序来关联它们的。超过 30 秒未处理的挂起请求会被清除。挂起请求队列的最大长度为 64——队列满时额外的请求会被丢弃。

服务等待与超时

行为值
服务客户端：等待可用性重试 10 次，每次 2 秒（共 20 秒）
服务客户端：响应超时30 秒
服务服务端：挂起请求上限64

动作（Action）桥接

动作（Action）客户端

从 Dora 向外部 ROS2 动作服务器发送目标，并接收反馈和结果。

nodes:
  - id: fib_client
    ros2:
      action: /fibonacci
      action_type: example_interfaces/Fibonacci
      role: client
    inputs:
      goal: goal_sender/goal
    outputs:
      - feedback
      - result

对每个 Arrow 目标输入：

  1. 将 Arrow 数据序列化为 Fibonacci_Goal CDR 消息
  2. 将目标发送到动作服务器（超时时间 30 秒）
  3. 若被接受，则启动后台线程来处理反馈和结果
  4. 反馈消息在流式到达时会通过 feedback 输出发出
  5. 最终结果会在 result 输出上到达（5 分钟超时）

反馈与结果流

动作桥接在不同的输出上分别发送反馈和结果：

  • feedback：每当动作服务器发来一条反馈消息时就流式发送。以 Arrow 形式包含该动作的反馈消息（例如 Fibonacci 的 {partial_sequence: int32[]}）
  • result：动作完成时发送一次。以 Arrow 形式包含该动作的结果消息（例如 Fibonacci 的 {sequence: int32[]}）

并发目标（Goals）

该桥接最多支持 8 个并发在途目标（MAX_CONCURRENT_GOALS）。超出的目标会被丢弃并记录警告。每个目标都会启动专用的反馈和结果读取线程。

超时

行为值
目标发送超时30 秒
结果获取超时5 分钟
反馈（Feedback）无超时（持续流式传输直到动作完成）

动作服务器

将一个 Dora 处理节点暴露为 ROS2 动作服务器，供外部 ROS2 客户端调用。

nodes:
  - id: fib_server
    ros2:
      action: /fibonacci
      action_type: example_interfaces/Fibonacci
      role: server
    inputs:
      feedback: handler/feedback
      result: handler/result
    outputs:
      - goal

  - id: handler
    path: path/to/handler-node
    inputs:
      goal: fib_server/goal
    outputs:
      - feedback
      - result

该桥接从 ROS2 客户端接收目标，自动接受，并在 goal 输出上转发目标数据。处理程序计算反馈和结果后，通过 feedback 和 result 输入把它们发回。

一个可运行的 Fibonacci 示例参见 examples/ros2-bridge/yaml-bridge-action-server/。

Goal ID 元数据

每个目标由一个以 goal_id 元数据参数传递的 UUID 字符串标识。桥接程序会在每个 goal 输出上设置 goal_id。处理函数在发送 feedback 和 result 时必须在元数据中包含相同的 goal_id，以便桥接程序能将它们与正确的目标关联起来。

最简单的做法是直接把 goal 事件中的 metadata.parameters 原样传递下去：

#![allow(unused)]
fn main() {
Event::Input { id, metadata, data } => match id.as_str() {
    "goal" => {
        let params = metadata.parameters; // contains goal_id
        // ... compute ...
        node.send_output("feedback".into(), params.clone(), feedback)?;
        node.send_output("result".into(), params, result)?;
    }
    // ...
}
}

动作服务器生命周期

  1. ROS2 客户端发送一个目标请求
  2. 桥接自动接受该目标并开始执行
  3. 桥接在 goal 输出上发送目标数据，元数据中带有 goal_id
  4. 处理程序发送 feedback（零次或多次），使用相同的 goal_id
  5. 处理程序发送 result（一次），使用相同的 goal_id；桥接将其返回给 ROS2 客户端
  6. 如果客户端从未请求结果，结果发送会在 5 分钟后超时

不包含任何数据或无法转发给处理程序的目标会被自动中止——桥接会向 ROS2 客户端返回 Aborted 状态，以避免其无限期挂起。

目标状态

默认情况下，结果以 Succeeded 状态返回。处理程序可以通过在结果输出上设置 goal_status 元数据参数来覆盖这一行为：

goal_status 取值ROS2 状态使用场景
"succeeded"（或省略）Succeeded目标成功完成
"aborted"Aborted目标在执行过程中失败
"canceled"Canceled目标被处理程序取消

无法识别的 goal_status 取值默认视为 Aborted，并记录警告。完全省略 goal_status 默认视为 Succeeded。

Rust 示例：

#![allow(unused)]
fn main() {
use dora_node_api::{GOAL_STATUS, GOAL_STATUS_ABORTED, Parameter};

let mut params = metadata.parameters; // contains goal_id
params.insert(GOAL_STATUS.to_string(), Parameter::String(GOAL_STATUS_ABORTED.to_string()));
node.send_output("result".into(), params, error_result)?;
}

Python 动作服务器处理程序

Python 节点以 PyArrow 数组形式接收目标数据，goal_id 位于元数据字典中。在反馈 / 结果输出中原样传递它：

for event in node:
    if event["type"] == "INPUT" and event["id"] == "goal":
        goal_id = event["metadata"]["goal_id"]
        order = event["value"]["order"][0].as_py()

        # Send feedback
        node.send_output("feedback", feedback_array, {"goal_id": goal_id})

        # Send result (with optional status)
        node.send_output("result", result_array, {
            "goal_id": goal_id,
            "goal_status": "succeeded",  # or "aborted", "canceled"
        })

服务质量（Quality of Service, QoS）

配置

可以在桥接级别设置 QoS（适用于所有话题 / 通道），也可以在多话题模式下按话题单独设置。

nodes:
  - id: my_bridge
    ros2:
      topic: /sensor/data
      message_type: sensor_msgs/LaserScan
      qos:
        reliable: true
        durability: transient_local
        keep_last: 10
        liveliness: automatic
        lease_duration: 5.0
        max_blocking_time: 0.5

lease_duration无限

按话题覆盖 QoS

在多话题模式下，每个话题可以覆盖桥接级别的 QoS：

nodes:
  - id: sensor_bridge
    ros2:
      topics:
        - topic: /fast_sensor
          message_type: sensor_msgs/Imu
          direction: subscribe
          qos:
            reliable: false          # override: best effort for this topic
            keep_last: 1
        - topic: /cmd
          message_type: geometry_msgs/Twist
          direction: publish
          # inherits bridge-level QoS (reliable: true)
      qos:
        reliable: true               # default for all topics
        keep_last: 10
    inputs:
      cmd: planner/cmd               # the `/cmd` publish topic's dora input
    outputs:
      - fast_sensor                  # the `/fast_sensor` subscribe topic's dora output

两个话题都没有设置 output: / input:，所以两者都使用由话题派生出的 id（fast_sensor、cmd）——和其他地方一样，这些 id 必须在节点上声明，否则配置会被拒绝。

数据格式：Arrow 结构体

节点与桥接之间交换的所有数据都使用只有一行的 Arrow StructArray。ROS2 消息中的每个字段都会成为结构体中的一列。

如何构建 Arrow 消息

Rust 示例：构建一个 AddTwoInts_Request（{a: i64, b: i64}）：

#![allow(unused)]
fn main() {
use std::sync::Arc;
use arrow::array::{Array, Int64Array, StructArray};
use arrow::datatypes::{DataType, Field};

fn make_add_request(a: i64, b: i64) -> StructArray {
    let fields = vec![
        Arc::new(Field::new("a", DataType::Int64, false)),
        Arc::new(Field::new("b", DataType::Int64, false)),
    ];
    let arrays: Vec<Arc<dyn Array>> = vec![
        Arc::new(Int64Array::from(vec![a])),
        Arc::new(Int64Array::from(vec![b])),
    ];
    StructArray::try_new(fields.into(), arrays, None)
        .expect("failed to create struct array")
}
}

读取响应（{sum: i64}）：

#![allow(unused)]
fn main() {
use arrow::array::{Int64Array, StructArray};

fn read_response(data: &dyn arrow::array::Array) -> i64 {
    let struct_array = data
        .as_any()
        .downcast_ref::<StructArray>()
        .expect("expected struct array");
    struct_array
        .column_by_name("sum")
        .expect("missing 'sum' field")
        .as_any()
        .downcast_ref::<Int64Array>()
        .expect("expected Int64Array")
        .value(0)
}
}

      # Single topic mode

          direction: publish

      service_type: package/TypeName   # ROS2 service type

      # Action mode (mutually exclusive with topic/topics/service)
      action: /action_name             # ROS2 action name
      action_type: package/TypeName    # ROS2 action type
      role: client                     # client | server

        keep_all: false                # true | false (default: false)

      # --- Optional ROS2 node config ---

2. 发布速度命令

nodes:
  - id: planner
    path: ./target/debug/planner
    inputs:
      tick: dora/timer/millis/100
    outputs:
      - cmd_vel

  - id: cmd_bridge
    ros2:
      topic: /turtle1/cmd_vel
      message_type: geometry_msgs/Twist
      direction: publish
    inputs:
      cmd_vel: planner/cmd_vel

#![allow(unused)]
fn main() {
// In planner: send geometry_msgs/Twist as Arrow
// Twist has nested Vector3 fields: linear {x,y,z} and angular {x,y,z}
fn make_twist(linear_x: f64, angular_z: f64) -> StructArray {
    let vec3_fields = vec![
        Arc::new(Field::new("x", DataType::Float64, false)),
        Arc::new(Field::new("y", DataType::Float64, false)),
        Arc::new(Field::new("z", DataType::Float64, false)),
    ];
    let linear = StructArray::try_new(
        vec3_fields.clone().into(),
        vec![
            Arc::new(Float64Array::from(vec![linear_x])) as _,
            Arc::new(Float64Array::from(vec![0.0])) as _,
            Arc::new(Float64Array::from(vec![0.0])) as _,
        ],
        None,
    ).unwrap();
    let angular = StructArray::try_new(
        vec3_fields.into(),
        vec![
            Arc::new(Float64Array::from(vec![0.0])) as _,
            Arc::new(Float64Array::from(vec![0.0])) as _,
            Arc::new(Float64Array::from(vec![angular_z])) as _,
        ],
        None,
    ).unwrap();

    let fields = vec![
        Arc::new(Field::new("linear", linear.data_type().clone(), false)),
        Arc::new(Field::new("angular", angular.data_type().clone(), false)),
    ];
    StructArray::try_new(
        fields.into(),
        vec![Arc::new(linear) as _, Arc::new(angular) as _],
        None,
    ).unwrap()
}
}

原生代码 API（Rust / Python / C++）

上面的 YAML 桥接与语言无关，节点代码中不需要任何 ROS2 代码。如果你希望改为在节点代码中命令式地驱动 ROS2——使用带类型的结构体、显式的请求/响应、目标句柄——请使用各语言对应的原生 API。它们封装的是同一套 ros2-client 技术栈；消息类型是在构建时，根据 AMENT_PREFIX_PATH 上的 .msg/.srv/.action 文件生成的。

这三种语言都支持话题的发布/订阅、服务客户端 + 服务器、以及动作客户端 + 服务器。完整可运行的示例见 examples/ros2-bridge/{rust,python,c++}/。

Python（dora.Ros2Context）

Python 节点先创建一个 ROS2 的 context 和 node，然后创建 publisher/subscription、服务/动作客户端/服务器，或参数。数据类型为 PyArrow。

from dora import Node, Ros2Context, Ros2NodeOptions, Ros2QosPolicies
import pyarrow as pa

dora_node = Node()                       # connect to the dora daemon FIRST
ctx = Ros2Context()
node = ctx.new_node("my_node", "/", Ros2NodeOptions(rosout=True))

qos = Ros2QosPolicies(reliable=True, keep_last=1)
方法用途
ctx.new_node(name, namespace, options, parameters=None)创建 ROS2 节点；parameters 用于声明初始的 ROS2 参数
node.create_topic(name, type, qos) / create_publisher(topic) / create_subscription(topic)话题的发布/订阅
node.create_service_client(name, type, qos=None) → Ros2ServiceClient.call(request, timeout_s=None)
node.create_service_server(name, type, qos=None) → Ros2ServiceServer.take_request() → (id, req) / None，然后调用 .send_response(id, resp)
node.create_action_client(name, type, qos) → Ros2ActionClient.send_goal(goal) → goal_id, .take_feedback(goal_id), .take_result(goal_id), .cancel(goal_id=None)
node.create_action_server(name, type, qos) → Ros2ActionServer.take_goal() → (goal_id, goal), .send_feedback(goal_id, fb), .send_result(goal_id, result, status=None), .take_cancel()
node.set_parameter / get_parameter / list_parameters / has_parameter运行时参数（同时提供给 ros2 param）

服务客户端示例（调用外部 ROS2 的 AddTwoInts）：

client = node.create_service_client("/add_two_ints", "example_interfaces/AddTwoInts", qos)
client.wait_for_service()
resp = client.call(pa.array([{"a": 2, "b": 3}]))
print(resp[0]["sum"].as_py())            # 5

参数（在创建节点时声明，随后提供给 ros2 param）：

node = ctx.new_node("demo", "/", Ros2NodeOptions(rosout=True),
                    parameters={"speed": 1.5, "name": "robot"})
node.set_parameter("speed", 2.0)
print(node.get_parameter("speed"), node.list_parameters())

阻塞调用（call、take_*）在等待期间会释放 GIL。参见 examples/ros2-bridge/python/{service-client,service-server,action-client,action-server,parameter}/。

C++ 节点包含生成的头文件，并调用带包命名空间的创建函数；数据类型为 rust::Box 或生成的结构体。服务和动作服务器由 matches / downcast 事件循环驱动，与客户端的方式类似。

#include "ros2-bridge/msg/example_interfaces.h"

auto server = example_interfaces::create_Fibonacci_action_server(
    *node, "/", "fibonacci", qos, merged_events);
// in the event loop:
if (server->matches(event)) {
    auto goal_event = server->downcast(std::move(event));
    auto goal = goal_event->get_goal();
    // ... compute ...
    server->publish_feedback(goal_event->get_goal_id(), feedback);
    server->send_result(goal_event->get_goal_id(), ActionStatusEnum::Succeeded, result);
}

发现与 RMW 说明（原生服务器）

  • 对于动作（action）而言，由 Dora 托管的服务器无法被真实的 rcl/rclcpp/rclpy 客户端发现（ros2-client#4）：动作示例是在同一个数据流中，将 Dora 服务器与 Dora 客户端配对使用。相比之下，服务（service）服务器可以被真实的 ros2 客户端正常发现。
  • RMW 必须匹配。服务/动作的关联方式在 Fast-DDS（Enhanced）和 Cyclone 的映射之间有所不同；桥接会根据 RMW_IMPLEMENTATION 选择对应的映射（原生代码在代码生成时确定，YAML 桥接在运行时确定）。不匹配会导致调用挂起。请在两端一致地设置 RMW_IMPLEMENTATION。
  • ros2-client 中没有 wait_for_action_server；如果没有服务器存在，客户端首次调用 send_goal 只会直接超时。

限制与已知约束

以下约束适用于 YAML / 动态桥接。原生代码 API 有其自己的说明，见发现与 RMW 说明（值得注意的是：Python 的动作客户端/服务器确实支持取消）。

  • 动作服务器自动接受：所有传入的目标都会被自动接受。handler 无法在执行开始前拒绝目标。
  • 不支持动作取消（YAML 桥接）：YAML 动作桥接不处理 ROS2 的取消请求（Python 原生动作 API 支持）。
  • 没有 wait_for_action_server：ros2_client 库不提供此 API。请在启动数据流之前先启动动作服务器。如果服务器不可用，第一个目标会在 30 秒后超时。
  • 原生动作服务器的发现问题（ros2-client#4）：由 Dora 托管的动作服务器无法被基于真实 rcl 的客户端发现；请将其与 Dora 客户端配对使用。服务服务器不受此影响。
  • 服务客户端单次并发：服务客户端按顺序处理请求——每个请求都会阻塞，直到收到响应（或在 30 秒后超时）。
  • 服务/动作通道的 QoS 是统一的：qos 配置适用于所有服务/动作子通道（goal、result、cancel、feedback、status）。无法针对单个通道单独配置 QoS。
  • 需要设置 AMENT_PREFIX_PATH：如果找不到 ROS2 消息定义，桥接会在启动时失败。
  • 最多 64 个话题：多话题模式下每个桥接节点最多支持 64 个话题。
  • 最多 8 个并发动作目标：达到上限后，新增目标会收到 Aborted 状态。
  • 最多 64 个待处理服务请求（服务端）：队列满时请求会被丢弃。

最佳实践

运行前请先 source 你的 ROS2 环境。确保已设置 AMENT_PREFIX_PATH，并包含所有所需的消息包。若未找到任何定义，桥接会记录一条错误日志。

请在数据流启动前先启动动作（Action）服务端。目前没有针对动作服务端的等待机制。如果服务端未就绪，首次发送目标会在 30 秒后超时。

对相关话题使用多话题模式。在同一个桥接节点上桥接 /turtle1/pose（订阅）和 /turtle1/cmd_vel（发布），比使用两个独立的桥接节点更能降低资源占用。

确保 Arrow 字段名与消息定义完全一致。桥接会校验 Arrow 结构体字段名是否与 ROS2 消息定义匹配。缺失的字段会使用默认值（数字为零、字符串为空）。多余的字段会导致错误。

在多话题模式下显式指定 output/input。默认的 ID 映射方式（去掉 /，再把 / 替换为 _）对于层级较深的话题名容易产生混淆。显式指定 ID 可以让 dataflow YAML 更具自说明性。

将 QoS 设置为与 ROS2 发布者 / 订阅者一致。QoS 不匹配（例如 reliable 的订阅者对应 best-effort 的发布者）会导致通信静默失败。可以用 ros2 topic info -v /topic_name 查看现有的 QoS 设置。

在服务响应中传递 request_id。桥接通过 request_id 元数据参数将响应与请求对应起来。如果处理函数的响应元数据中没有包含 request_id，桥接就无法将该响应匹配到对应的原始 ROS2 请求。
