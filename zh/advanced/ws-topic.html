Dora 用户指南

WebSocket Topic 数据通道

topic 数据通道扩展了 WebSocket 控制平面，用于将协调器中的实时数据流消息代理转发给 CLI 客户端。这样一来，topic echo、topic hz、topic info 等 CLI 命令就不再需要直接访问 Zenoh 网络，而是通过现有的 WebSocket 连接以二进制帧的形式接收消息数据。

动机

场景之前（直接使用 Zenoh）之后（WS 代理）
CLI 与守护进程在同一台机器上可行可行
CLI 远程，Zenoh 可达可行可行
CLI 远程，无法访问 Zenoh失败可行
基于浏览器的 Web UI无法实现可以实现
嵌入式目标设备，没有本地磁盘无法在本地录制--proxy 流式传输到 CLI

关键思路在于：CLI 以及未来的 Web UI 都通过 WebSocket 连接到协调器。让协调器代表它们订阅 Zenoh，并以二进制帧的形式转发消息，这样只要 WebSocket 连接能到达的地方，就能进行 topic 检查。

架构

CLI  ──── WS (binary frames) ────>  Coordinator  ──── Zenoh sub ────>  Daemon
                                    (Zenoh proxy)                      (debug publish)

协调器充当 Zenoh 代理：

  1. CLI 通过现有的文本帧 WS 协议发送 TopicSubscribe 请求
  2. 协调器验证该数据流并打开 Zenoh 订阅者
  3. 协调器将每个 Zenoh 样本作为二进制 WS 帧转发回 CLI
  4. CLI 根据订阅 UUID 将二进制帧分发给相应的消费者

线路协议

订阅握手（JSON 文本帧）

该订阅使用现有的基于 UUID 关联的请求-响应协议：

请求（CLI -> 协调器）：

{
  "id": "abc-123",
  "method": "control",
  "params": {
    "TopicSubscribe": {
      "dataflow_id": "550e8400-...",
      "topics": [["camera_node", "image"], ["lidar_node", "points"]]
    }
  }
}

响应（协调器 -> CLI）：

{
  "id": "abc-123",
  "result": {
    "TopicSubscribed": {
      "subscription_id": "7f1b3a00-..."
    }
  }
}

取消订阅（CLI -> 协调器）：

{
  "id": "def-456",
  "method": "control",
  "params": {
    "TopicUnsubscribe": {
      "subscription_id": "7f1b3a00-..."
    }
  }
}

二进制数据帧

握手完成后，协调器会推送二进制 WS 帧。每个帧都有一个固定大小的头部：

 0                   16                              N
 ├───────────────────┼──────────────────────────────┤
 │  subscription_id  │  Timestamped<InterDaemonEvent>│
 │  (16 bytes UUID)  │  (postcard serialized)        │
 └───────────────────┴──────────────────────────────┘
字段大小描述
subscription_id16 bytes与 TopicSubscribed 确认（ack）匹配的 UUID，用于多路复用
payload可变来自 Zenoh 的原始 Timestamped<InterDaemonEvent> postcard 字节

16 字节的 UUID 前缀使得在单个 WS 连接上多路复用多个订阅成为可能，而无需额外的帧开销。

协议版本

上述帧不携带封装信息，也不使用自描述编码，因此如果对端使用不同的二进制格式，会错误解析这些帧，而不是解码失败。因此订阅握手会交换版本号，任一方在版本不匹配时都会拒绝该订阅：

版本负载编码
（缺失）1.0 之前，bincode——早于此握手机制
1bincode
2postcard（当前，dora_message::TOPIC_DATA_PROTOCOL_VERSION）

TopicSubscribe 携带客户端的版本，TopicSubscribed 携带协调器的版本：

{"TopicSubscribe":  {"dataflow_id": "...", "topics": [...], "protocol_version": 2}}
{"TopicSubscribed": {"subscription_id": "...", "protocol_version": 2}}

这两个字段都是 #[serde(default)]，因此早于该握手机制的对端会直接省略它们——这会反序列化为 None，并因与错误版本号相同的原因被拒绝。拒绝信息会同时指出双方的版本，便于操作者判断哪一方版本过旧：

topic data protocol mismatch: client predates the topic data protocol handshake
(bincode-era frames), this side speaks 2.
Binary frames are positionally encoded, so subscribing would silently misparse
rather than fail. Upgrade whichever side is older.

每当二进制负载编码发生变化时，都应递增 TOPIC_DATA_PROTOCOL_VERSION。JSON 握手本身是自描述的，不需要递增。

数据流

CLI                         WsSession                     Coordinator
 │                              │                              │
 │── subscribe_topics() ───────>│                              │

 │                              │                              │ spawn subscriber tasks
 │                              │<── WsResponse{TopicSubscribed}│
 │<── (sub_id, data_rx) ───────│                              │
 │                              │                              │
 │                              │       ┌── Zenoh sample ──────│ Daemon publishes
 │                              │<──────│ Binary frame         │
 │<── data_rx.recv() ──────────│       │ (sub_id + payload)   │
 │                              │       │                      │
 │                              │<──────│ Binary frame         │
 │<── data_rx.recv() ──────────│       │                      │
 │                              │       └                      │
 │                              │                              │

协调器内部实现

  1. 校验：ControlEvent::TopicSubscribe 会被发送到协调器事件循环，该循环会检查数据流是否存在，并确认其已启用 enable_debug_inspection: true
  2. 延迟初始化 Zenoh：协调器的 Zenoh 会话会在第一次 TopicSubscribe 请求时打开，并在同一 WS 连接上后续的订阅中复用
  3. 按话题分配任务：每个 (node_id, data_id) 组合都会启动一个 tokio 任务，订阅对应的 Zenoh 话题，并将样本转发到二进制帧通道
  4. 背压：二进制帧通道的容量为 64。使用 try_send——如果通道已满（消费者过慢），样本会被静默丢弃，而不是阻塞 Zenoh 订阅者
  5. 清理：当 WS 连接关闭时，所有订阅者任务都会被终止

WsSession（CLI 端）

WsSession::subscribe_topics() 方法：

  1. 序列化一个 TopicSubscribe 请求
  2. 通过内部命令通道发送 SessionCommand::SubscribeTopics
  3. 异步的 session_loop 将其包装为 WsRequest 并发送
  4. 收到 TopicSubscribed 确认后，将 data_tx 发送端以 subscription_id 为键注册到 topic_subscribers 中
  5. 二进制帧的分发方式是提取前 16 字节作为 UUID，并将剩余部分发送到对应的 data_tx

session_loop 中维护的状态：

  • pending_topic_subscribes: HashMap<Uuid, (ack_tx, data_tx)>——等待确认
  • topic_subscribers: HashMap<Uuid, Sender>——正在接收二进制数据的活跃订阅

前置条件

数据流描述文件必须启用调试消息发布：

debug:
  enable_debug_inspection: true

如果未启用，协调器会拒绝 TopicSubscribe，并返回：

dataflow {id} not found or enable_debug_inspection not enabled

CLI 命令

dora topic echo

将话题数据实时流式传输到终端。

# Echo a single topic
dora topic echo -d my-dataflow camera_node/image

# Echo multiple topics
dora topic echo -d my-dataflow robot1/pose robot2/vel

# JSON output for piping
dora topic echo -d my-dataflow robot1/pose --format json

内部实现：调用 session.subscribe_topics()，从 data_rx 通道接收 Timestamped<InterDaemonEvent>，反序列化 Arrow 数据，并以表格或 JSON 形式渲染。

dora topic hz

交互式 TUI，显示按话题统计的发布频率信息。

# All topics
dora topic hz -d my-dataflow --window 10

# Specific topics
dora topic hz -d my-dataflow robot1/pose robot2/vel --window 5

TUI 使用 ratatui 实现。后台的 std::thread 从 data_rx 接收事件，并通过 BTreeMap<(node_id, data_id), index> 查找，分发到各话题对应的 HzStats 追踪器。

dora topic info

一次性获取话题元数据和统计信息。

dora topic info -d my-dataflow camera_node/image --duration 5

收集 --duration 秒内的消息，然后显示类型信息、发布者、订阅者（来自描述文件）、消息数量和带宽。

dora record --proxy

通过 WebSocket 流式传输数据流数据以进行本地录制。

# Start dataflow first
dora start dataflow.yml --detach

# Record via proxy (data streams through coordinator to CLI)
dora record dataflow.yml --proxy -o capture.drec

# Record specific topics
dora record dataflow.yml --proxy --topics sensor/image,lidar/points

使用场景：目标机器（运行守护进程）没有本地磁盘或存储空间有限。--proxy 标志会将数据通过协调器 WebSocket 路由到 CLI 所在机器，.drec 文件会在该机器本地写入。

如果不使用 --proxy（默认情况），会向数据流中注入一个 record 节点，直接在守护进程所在机器上进行录制。

Zenoh 话题格式

协调器使用 dora_core::topics::zenoh_output_publish_topic() 中定义的格式订阅 Zenoh 话题：

dora/{dataflow_id}/{node_id}/{data_id}

每个话题都以 Timestamped<InterDaemonEvent> 作为负载，使用 postcard 序列化——这是一种紧凑、非自描述的二进制格式，拥有已记录且稳定的线上协议规范。协调器会按原样转发这些字节（前面附加订阅 UUID）——不做重新序列化。

线上协议变更（dora 1.0）：在 1.0 之前，该负载采用 bincode 编码。两种格式都是按位置编码的，因此 bincode 时代的订阅者在面对 postcard 帧时不会干净地失败——而是会错误解析它们。订阅握手会在双方都携带 protocol_version，正是为了让不匹配的情况在订阅时就被拒绝，而不是以数据损坏的形式出现；参见下方的协议版本。

背压与性能

参数值理由
二进制帧通道容量64在延迟和内存之间取得平衡
丢弃策略满时丢弃优先保证新鲜度而非完整性
二进制格式原始 postcard（不使用 base64）避免大负载产生 33% 的额外开销

对于高吞吐量话题（摄像头图像、点云），如果 WS 连接速度较慢，二进制帧通道可能会被填满。丢弃的样本是静默的——CLI 会在 topic hz 中显示降低的频率，但不会卡住。

错误处理

错误来源响应
数据流未找到协调器校验带错误消息的 WsResponse
未启用 enable_debug_inspection协调器校验带错误消息的 WsResponse
Zenoh 会话打开失败协调器带错误消息的 WsResponse
Zenoh 订阅者失败按话题的任务记录警告日志，任务退出
二进制帧过短（<16 字节）CLI session_loop记录警告日志，帧被丢弃
未知的订阅 UUIDCLI session_loop帧被静默丢弃
WS 连接关闭任一侧所有任务中止，待处理的 ack 返回错误
